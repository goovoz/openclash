# 03 · 路径契约与行为契约

> **本文是 `openclash-rt` 的接口规范，不是设计建议。**
> 契约来自对上游 `vernesong/OpenClash` 源码的**逐行测绘**，每一项都标注了
> 上游文件:行号。兼容层、`.deb` 布局、端到端测试都必须以本文为准。
>
> 基线：`PKG_VERSION=0.47.156`，`COMMIT=c3a33c1d3407956fdf8f0e0b7c1a4c52e6ad9593`
> 测绘方法见 [附录 A](#附录-a测绘方法可复现)，可随时对上游新版本重跑。

---

## 0. 为什么需要"契约"这个词

上游 OpenClash 是**为 OpenWrt 写死的**：它不通过变量、不走配置、不做探测，
而是**直接假设这些绝对路径存在**。全文一共 342 处 `inet fw4`、146 处
`/usr/share/openclash/**`、178 处 `/etc/openclash/**`，全部是硬编码字面量。

这带来一个**硬约束**：

> **兼容层不能"把上游改成可配置的"，只能"在上游假设的位置上把东西摆好"。**

这是"100% 复刻 + 可持续同步上游"两个目标能同时成立的唯一前提。任何"改上游
让它支持 Debian"的做法都会在下次 `git pull` 时产生冲突，违背可同步目标。

因此本文把上游的隐性假设**显式化**成两类契约：

| 契约类型 | 含义 | 违反后果 |
|---|---|---|
| **文件路径契约** | 上游会以绝对路径 `source`／执行／读写某个文件 | 脚本直接报 `not found`，功能整体失效 |
| **行为契约** | 上游假设某个**外部设施**已经存在并带有特定语义 | 静默降级，不报错但功能不生效（**更危险**） |

**行为契约比路径契约危险得多**，因为它不产生错误信息。例如 `FW4` 为空时
上游会安静地跳过整段分流逻辑（见 §2.3）。

## 1. 文件路径契约

### 1.1 兼容层**必须提供**的路径（否则脚本报错）

| 路径 | 类型 | 上游引用点（示例） | 引用数 | 由谁提供 |
|---|---|---|---|---|
| `/etc/rc.common` | 解释器 | `init.d/openclash:1` → `#!/bin/sh /etc/rc.common` | — | 兼容层 |
| `/lib/functions.sh` | `source` | `init.d/openclash:3058`、`openclash.sh:2`、`uci.sh:2`、`yml_*.sh:2` | 11 文件 | 兼容层（OpenWrt 原文件） |
| `/lib/functions/procd.sh` | `source` | `openclash.sh:6` | 1 | 兼容层（自研垫片） |
| `/lib/functions/service.sh` | `source` | `rc.common` 内部按需 | — | 兼容层（桩） |
| `/lib/functions/network.sh` | `source` | `functions.sh` 按需 | — | 兼容层（OpenWrt 原文件） |
| `/lib/config/uci.sh` | `source` | `functions.sh` 末尾按需 | — | 兼容层（OpenWrt 原文件） |
| `/sbin/uci` | 可执行 | `config/uci.sh` → `uci_load()` | 1（但被 257 处 `config_get` 间接依赖） | 兼容层（自建 uci 二进制） |
| `/usr/share/openclash/*.sh` | `source`／可执行 | 全部脚本（34 个文件，9198 行） | 146 | 上游原样安装 |
| `/etc/init.d/openclash` | 可执行 | init 脚本本体（3848 行） | — | 上游原样安装 |

`/lib/config/uci.sh` 里的调用形态（这是 `/sbin/uci` 必须存在的直接原因）：

```sh
uci_load() {
	local PACKAGE="$1"
	local DATA
	local RET
	...
	DATA="$(/sbin/uci ${UCI_CONFIG_DIR:+-c "$UCI_CONFIG_DIR"} \
		${LOAD_STATE:+-P /var/state} -S -n export "$PACKAGE" 2>/dev/null)"
	RET="$?"
	eval "$DATA"
	return ${RET:-0}
}
```

> **`-S -n export` 三个参数是必须支持的**：`-S` 强制按配置序输出，
> `-n` 只输出名字不输出类型，`export` 渲染成 `CONFIG_<sec>_<opt>=<val>`
> 供 `eval`。少了任何一个，`config_get` 全线返回空。

### 1.2 上游**自己创建**的路径（兼容层不应预置）

| 路径 | 语义 | 首次创建点 |
|---|---|---|
| `/etc/openclash/` | 核心与应用数据目录（178 次引用） | `init.d/openclash:566` `mkdir -p` |
| `/etc/openclash/clash` | **指向核心的符号链接**（见 §2.5） | `init.d/openclash:568` `ln -s` |
| `/etc/openclash/core/clash_meta` | mihomo 核心二进制 | 用户/UI 下载 |
| `/etc/openclash/cache.db` | 运行缓存 | 运行时 |
| `/etc/openclash/custom/*.list` | 自定义直连/规则列表 | 运行时 |
| `/etc/config/openclash` | **UCI 主配置**（`enable`、`en_mode` 等） | 包内 conffile 提供初值 |
| `/etc/config/dhcp` | 上游会写 `dhcp.@dnsmasq[0].*` | 兼容层提供空壳，上游写入 |
| `/etc/crontabs/` | 目录本身在 Debian 不存在 | **兼容层必须 `mkdir`**（见 §2.6） |
| `/tmp/openclash*.log` | 日志（`/tmp` 在 Debian 可写，无障碍） | 运行时 |

> ⚠️ **`/etc/config/` 是 OpenWrt 的 UCI 配置树**，不是 Debian 的 `/etc`。
> 它是一个**独立概念**，`.deb` 需要创建这个目录并放入 `openclash`／`dhcp` 两个文件。
> 这与 Debian 的任何现有路径都不冲突（`/etc/config` 在 Debian 上原本为空）。

### 1.3 特殊文件：`/etc/openwrt_release`

`init.d/openclash` **第 14 行**：

```sh
[ -f /etc/openwrt_release ] && {
FW4=$(command -v fw4)
DEFAULT_DNSMASQ_CFGID="$(uci -q show "dhcp.@dnsmasq[0]" | awk 'NR==1 {split($0, conf, /[.=]/); print conf[2]}')"
if [ -f "/tmp/etc/dnsmasq.conf.$DEFAULT_DNSMASQ_CFGID" ]; then
   DNSMASQ_CONF_DIR="$(awk -F '=' '/^conf-dir=/ {print $2}' "/tmp/etc/dnsmasq.conf.$DEFAULT_DNSMASQ_CFGID")"
else
   DNSMASQ_CONF_DIR="/tmp/dnsmasq.d"
fi
DNSMASQ_CONF_DIR=${DNSMASQ_CONF_DIR%*/}
}
```

这个文件是上游的**"我是不是在 OpenWrt 上"开关**，它同时决定了
`DNSMASQ_CONF_DIR` 的推导。**如果不提供它，`DNSMASQ_CONF_DIR` 保持未定义**，
后续所有 `mkdir -p ${DNSMASQ_CONF_DIR}` 与 `>>${DNSMASQ_CONF_DIR}/...` 会写到
根目录 `/` 或直接失败。

**做法：`.deb` 安装一个"伪" `/etc/openwrt_release`**，让该分支成立，同时给出
正确的 `DISTRIB_*` 值（上游 `uci-defaults` 与部分 Lua 用它推断内核架构）。

```sh
DISTRIB_ID='openclash-rt'
DISTRIB_RELEASE='debian'
DISTRIB_TARGET='debian/amd64'
DISTRIB_ARCH='amd64'          # 必须与 dpkg --print-architecture 一致
DISTRIB_DESCRIPTION='OpenClash runtime for Debian/Ubuntu (openclash-rt)'
```

> ✅ **这是"零改动"路线的一个关键技巧**：不改上游、不加补丁，只把上游的
> `[ -f ... ]` 条件喂成真，就解锁了整段 DNS 逻辑。

### 1.4 Lua 解释器与 C 模块搜索路径契约

这一节是 `runtime/lua/lua-path-bridge.sh` 与 `runtime/upstream/pin-lua-interpreter.sh`
的唯一权威依据。两条契约互不相同，都容易搞混。

#### 1.4.1 解释器：必须是**绝对路径**的 Lua 5.1

上游有 **11 处**假定「`lua` 这个命令解析到 Lua 5.1」（清单见 `docs/04` §2.3）。
**不能依赖 `/usr/bin/lua`**：

| 事实 | 证据 |
|---|---|
| Debian 用 update-alternatives 组 **`lua-interpreter`** 提供 `/usr/bin/lua` | `update-alternatives --config lua-interpreter` |
| 优先级 `lua5.1`=**110** < `lua5.2`=120 ≈ `lua5.3`=120 < `lua5.4`=**130** | 同上（实测输出） |
| ⇒ 机器上只要有 lua5.4，`/usr/bin/lua` 就指向 5.4 | 同上 |

后果：为 5.1 编译的 `nixio.so`/`lucihttp.so`/`ubus.so` 在 5.4 下以
`undefined symbol: lua_...` 失败，**症状与「搜索路径没桥接对」几乎一样**。

⇒ **契约：打包期把 11 处全部改写成 `/usr/bin/lua5.1`**，由
`runtime/upstream/pin-lua-interpreter.sh` 完成（`upstream/` 源树不动）。
**不**注册 `update-alternatives`：那会改全系统的 `lua`，且该组处于 manual
模式时新候选不会生效，等于没有保证。

#### 1.4.2 C 模块：Debian 的默认搜索路径**不含** `/usr/lib/lua/`

Debian `lua5.1` 的 `luaconf.h` 来自 Lua 上游 5.1.4-6 起的补丁，形如
（Debian bug #671286 / Launchpad #977813 给出了原文）：

```c
#define LUA_CDIR2  LUA_ROOT2 "lib/" DEB_HOST_MULTIARCH "/lua/5.1/"
#define LUA_CPATH_DEFAULT \
    "./?.so;" LUA_CDIR"?.so;" LUA_CDIR2"?.so;" LUA_CDIR3"?.so;" LUA_CDIR"loadall.so"
```

Debian Lua 维护者在 lua-users 邮件列表给出的实机输出亦可对照：

```
./?.so;/usr/local/lib/lua/5.1/?.so;/usr/lib/lua/5.1/?.so;...
```

于是：

| 目录 | 在默认 `cpath` 里？ |
|---|---|
| `/usr/lib/lua/5.1/?.so` | ✅ **在**（`LUA_CDIR"?.so"`） |
| `/usr/lib/<multiarch>/lua/5.1/?.so` | ✅ 在（`LUA_CDIR2"?.so"`） |
| `/usr/local/lib/lua/5.1/?.so` | ✅ 在（`LUA_CDIR3"?.so"`） |
| **`/usr/lib/lua/?.so`** | ❌ **不在**（少了 `5.1/` 这一层） |

而**上游契约恰恰是把 `.so` 放在 `/usr/lib/lua/` 下**（`nixio.so`、`lucihttp.so`、
`luci/ip.so`、`luci/jsonc.so`、`luci/template/parser.so`）—— 那是 OpenWrt 的布局，
不是 Debian 的。两边都动不了，只能在中间架桥：

> **契约：`/usr/lib/lua/**` 下的每个模块，都要在 Debian 默认搜索路径里有一个
> 指向它的软链。** 由 `runtime/lua/lua-path-bridge.sh` 完成，且**必须建在
> 编译期默认搜索路径上**（而不是靠 `LUA_CPATH`/`LUA_PATH` 环境变量）——
> 因为上游的 CLI 调用方（cron 里的 `openclash_watchdog.sh`、`openclash_core.sh`）
> 不会帮我们设环境变量。

**唯一的例外**：`ubus.so` 由 `runtime/ubus/build-ubus.sh` 直接装到
`/usr/lib/lua/5.1/ubus.so` —— 正好落在上面 ✅ 那一行，**不需要任何桥接**。
（注意 ubus 的 `lua/CMakeLists.txt:3` 有 `SET(CMAKE_INSTALL_PREFIX /)`，
它自己装到的位置是 `/lib/lua/5.1/`，必须显式搬运，见 `docs/04` §5.3。）

> **推论**：判断"某个 `.so` 要不要桥接"只需一条：**它的落点是
> `/usr/lib/lua/<模块>.so`（无 `5.1`）就必须桥接；落在 `/usr/lib/lua/5.1/` 就不用。**

#### 1.4.3 钉定的**范围**：哪些文件要处理，哪些不要

上面两条契约最终都要落到具体文件上，而"范围"本身是个容易搞错的决定。
实测踩到两点，各自导致过一个静默缺口：

**① 上游有两个 lua 入口没有扩展名。**

| 文件 | 首行 | 作用 |
|---|---|---|
| `luci-base/htdocs/cgi-bin/luci` | `#!/usr/bin/lua` | **整个 Web UI 的 CGI 入口** |
| `luci-base/root/usr/libexec/rpcd/luci` | `#!/usr/bin/env lua` | rpcd 的 Lua 插件 |

它们的文件名都叫 `luci`，**没有 `.lua` 后缀**。而 `--dir` 模式是按
`-name '*.<ext>'`（默认 `lua sh`）枚举的，因此它**永远选不到这两个文件** ——
这两个入口的 shebang 会被静默漏掉（第二个更隐蔽：`env` 走 `PATH`，
同样会被 lua5.4 劫持）。

⇒ `pin-lua-interpreter.sh` 提供 `--file <路径>`（可重复）模式，
**刻意不过滤扩展名**：

```sh
runtime/upstream/pin-lua-interpreter.sh \
    --file "<staging>/usr/share/luci/htdocs/cgi-bin/luci" \
    --file "<staging>/usr/libexec/rpcd/luci"
```

（`--file` 与 `--dir` / `--check <目录>` **不能混用**：两种范围语义重叠，
混用会得到一个说不清的扫描范围，工具直接拒绝。）

**② 不能对整棵 `vendor/luci` 跑宽判据。**

宽判据 `RESIDUAL_RE` 刻意写得比改写规则**更宽**（设计理由见工具头部），
代价是会把"散文里恰好出现 lua 一词"的位置也算进来。实测在 `vendor/luci`
上有 **3 处误报**：

| 文件 | 命中内容 | 性质 |
|---|---|---|
| `luci-lib-nixio/root/usr/lib/lua/nixio/fs.lua:2` | `nixio - Linux I/O library for lua` | `--[[` 块注释 |
| `luci-lib-nixio/root/usr/lib/lua/nixio/util.lua:2` | 同上 | `--[[` 块注释 |
| `luci-lib-nixio/axTLS/samples/lua/axssl.lua:42,43` | `-- > [lua] axssl s_server -?` | 注释 |

⇒ **正确做法是按显式路径钉定，而不是放宽判据** —— 放宽会连带削弱
`upstream/openclash` 那棵树上的告警能力，而那里才是「上游同步冲突告警」的落点。

> **范围契约**：
> | 范围 | 方式 | 命中 |
> |---|---|---|
> | `/usr/share/openclash/**`（33 个 `.lua`/`.sh`） | `--dir` | 11 处 |
> | LuCI 的两个无扩展名入口 | `--file` | 各 1 处 |
> | `vendor/luci/luci/**` 等纯 Lua 模块 | **不处理** | —— 它们是 `require` 进来的，不被内核按 shebang 执行 |
> | `vendor/luci/luci-lib-nixio/axTLS/**` | **不处理**，也不随包发布 | TLS 示例树 |
>
> 实测 `grep -rn '^#!.*lua' vendor/luci` 只命中 **5 处**：上表那两个入口 +
> axTLS 的 3 个示例。也就是说除这两个入口外，vendor 树里没有别的可执行 lua 入口。

## 2. 行为契约

### 2.1 服务管理：`procd` + `rc.common`

**契约**：`/etc/init.d/openclash` 的第 1 行是 `#!/bin/sh /etc/rc.common`，
内核会执行 `/bin/sh /etc/rc.common <脚本> <动作> [参数]`。

上游实际用到的 `procd` API 面（已逐一核对，共 **3 个文件 14 处**）：

| API | 上游调用点 |
|---|---|
| `procd_open_instance` | `init.d:815`(start_run_core)、`init.d:3786`(start_watchdog) |
| `procd_set_param` | `init.d:819-824`（command/user/group/limits/respawn/stderr/env） |
| `procd_append_param` | 同族 |
| `procd_close_instance` | `init.d:826`、`init.d:3788` |
| `procd_running` | `rc.common` 的 `running` 动作 |
| `procd_kill` | `rc.common` 的 `stop` 动作 |
| `procd_send_signal` | `rc.common` 的 `reload`/`signal` 动作 |
| `procd_open_service`／`procd_close_service`／`procd_lock` | `rc.common` 自身 |

**上游原样的调用块**（`init.d/openclash:814–826`）：

```sh
procd_open_instance "openclash-core"                       # 实例名
procd_set_param env SAFE_PATHS=/usr/share/openclash:/etc/ssl
procd_set_param command /bin/sh -c "exec $CLASH -d $CLASH_CONFIG -f \"$CONFIG_FILE\" >> $LOG_FILE 2>&1"
procd_set_param user "root"
procd_set_param group "nogroup"
procd_set_param limits nproc="unlimited" as="unlimited" memlock="unlimited" nofile="1000000 1000000"
procd_set_param respawn 300 5 3
procd_set_param stderr 1
procd_close_instance
```

**兼容层语义映射**（实现在 `runtime/procd/procd.sh`）：

| procd | systemd | 说明 |
|---|---|---|
| service | 一组单元 + 注册表 `$RT/services/<svc>.instances` | 一个 init 脚本可起多个实例 |
| instance | `openclash-rt-<instance>.service` | 一实例一单元 |
| `command` | wrapper 脚本 `exec 'argv1' 'argv2'...` + `ExecStart=/bin/sh <wrapper>` | **必须用 wrapper 而非直接 `ExecStart`**，因为上游 `command` 的 argv 里含 shell 重定向字符串 |
| `env` | `Environment=`（含引号转义） | |
| `user`/`group` | `User=`/`Group=` | `nogroup` 在 Debian 存在（gid 65534） |
| `limits` | `Limit*=` | `unlimited` → `infinity`；`nofile="A B"` 取 soft 值 A |
| `respawn 300 5 3` | `Restart=always` + `StartLimitIntervalSec=300` + `RestartSec=5` + `StartLimitBurst=3` | **顺序是 threshold/timeout/retry** |
| `stderr 1` | `StandardError=journal` | 兜底；上游自身已重定向到 `$LOG_FILE` |

> **为什么用 `Type=simple` 而不是 `oneshot`**：核心进程是长期驻留的前台进程，
> 且需要 `Restart=always` 语义（对应 procd `respawn`）。
> `openclash.service` 本身用 `Type=oneshot` + `RemainAfterExit=yes`，
> 它只负责触发 `/etc/init.d/openclash boot`；真正的核心在动态生成的
> `openclash-rt-openclash-core.service` 里跑。

**shell 方言契约**：上游脚本混用 ash/bash 语法（`${var:0:0}`、`${var:0:-1}`、
`==` 比较），而 Debian 的 `/bin/sh` 是 **dash**。兼容层在 `/etc/rc.common`
开头做一次 **re-exec 到 bash**，**不改上游一行**：

```sh
if [ -z "${BASH_VERSION:-}" ] && [ -z "${_OC_RT_REEXEC:-}" ]; then
    _oc_rt_sh="${OPENCLASH_RT_SHELL:-/bin/bash}"
    [ -x "$_oc_rt_sh" ] && { _OC_RT_REEXEC=1; export _OC_RT_REEXEC; exec "$_oc_rt_sh" "$0" "$@"; }
fi
```

> 注意：`#!/bin/sh /etc/rc.common` 这种"解释器 + 参数"的 shebang 在 Linux 上是
> 合法的（内核把 `/etc/rc.common` 当作第 1 个参数传给 `/bin/sh`），
> 但 `$0` 会变成 `/etc/rc.common`，真实脚本名在 `$1`。`rc.common` 必须自己做
> `initscript="$1"; shift` 的搬运——上游 `rc.common` 就是这么做的。

### 2.2 UCI 契约

**契约**：`/sbin/uci` 是一个功能完整的 UCI CLI，且 `/etc/config/` 下必须有
**5 个包**存在：

| 包 | 上游做了什么 | 兼容层是否提供 |
|---|---|---|
| `openclash` | 读写 14 个 `config` 选项（`enable`/`en_mode`/`core_type` …） | ✅ 提供（conffile） |
| `dhcp` | **写** `dhcp.@dnsmasq[0]` 的 7 个选项 | ✅ 提供，见 §2.4 |
| `firewall` | **写** `firewall.openclash`（include 注册） | ✅ 提供，见 §2.3.5 |
| `ucitrack` | **写** `ucitrack.@openclash[-1].init` | ✅ 提供空壳 |
| `network` | **读** `network.lan.ipaddr` / `.ifname` / `.device` | ✅ 提供，见 §2.9 |

上游对 `dhcp.@dnsmasq[0]` 写入的完整选项集（7 个，`grep` 实测）：

```
cachesize   filter_aaaa   localuse   noresolv   port   resolvfile   server
```

| 需求 | 说明 |
|---|---|
| `uci get/show/set/add/delete/commit/revert/changes/rename/add_list/del_list` | 上游全部用到 |
| `uci export -S -n` | `uci_load()` 依赖，见 §1.1 |
| `uci -q show "dhcp.@dnsmasq[0]"` | `init.d:16` 用它取 dnsmasq 段 ID（见 §2.4.2） |
| 匿名段 `@dnsmasq[0]`、`@openclash[-1]` | 上游大量使用 |
| `uci -q -p /tmp/state get ...` | `-P` 状态目录参数（`init.d:3527`） |
| `uci add_list openclash.config.dnsmasq_server=...` | `save_dnsmasq_server()` |

**兼容层做法**：编译 OpenWrt 官方 `uci`（含 `libubox`）+ 提供 `/etc/config/*`。
**不使用 mock**——真实 `uci` 语义（尤其是匿名段与 `add_list`）差异太大，
mock 会在长期运行中制造难以定位的偏差。

> ⚠️ `network` 与 `firewall` 这两个包在 Debian 上**原本不存在**，
> 而 `/etc/config/` 这个目录树本身就是 OpenWrt 概念（不是 Debian 的 `/etc`）。
> 因此**不存在覆盖系统文件的风险**，`/etc/config/` 在 Debian 上原本为空。

#### 2.2.1 `/sbin/uci` 的落位与**所有权**契约

上游 `uci_load()` 硬编码 `/sbin/uci`，而 Debian 的 uci 装在 `/usr/sbin/uci` 或
`/usr/bin/uci`。补齐这个路径**不是**一句 `ln -sf` 就完事的 —— 有两个坑，且两个
都只在**特定主机**或**特定操作**上才暴露。

**坑 1：usrmerge 主机上的自指链接。**
Debian 12+ / Ubuntu 24.04 默认 usrmerge，`/sbin` 本身就是 `→ usr/sbin` 的符号
链接。此时 `/sbin/uci` 与 `/usr/sbin/uci` **是同一个文件**；再执行
`ln -sf /usr/sbin/uci /sbin/uci`，等于在一个路径上创建指向自己的链接：GNU `ln`
报 `'x' and 'x' are the same file` 并以非零退出 —— 而 `postinst` 有 `set -e`，
于是**安装直接失败**（dpkg 报配置错误）。

判定必须比较 inode：

| 判据 | 可靠 | 原因 |
|---|---|---|
| `[ /sbin -ef /usr/sbin ]` | ✅ | inode 相同才是"同一目录"的充分条件，与 `/sbin` 是真实目录还是链接无关 |
| `[ -L /sbin ]` | ❌ | 只说明它是链接，不说明它指向谁；也不能排除被手工拆开的 usrmerge |
| `readlink /sbin` | ❌ | usrmerge 下返回相对路径 `usr/sbin`，拼绝对路径要靠人；非 usrmerge 下返回空 |

**坑 2：卸载时的"不建但会删"。**
这是同一功能的另一半，也更隐蔽。曾经的实现是：`postinst` 用
`[ ! -e /sbin/uci ]` 守卫后才创建，而 `postrm purge` 里另有一句**无条件**的
`rm -f /sbin/uci`。于是当 `/sbin/uci` 属于别的包时：

| 阶段 | 旧行为 | 期望 |
|---|---|---|
| 安装 | `postinst` 见到已存在 → 跳过创建 ✅ | 一致 |
| 卸载 | `postrm purge` 无条件 `rm -f` → **把它删掉** ❌ | 必须保留 |

现象是"卸载了 openclash-rt，另一个工具的 `uci` 命令也不见了"，而报错现场离真因
极远。**故删除必须凭所有权凭据**，具体协议：

1. **创建侧**（`postinst`）：usrmerge（`/sbin -ef /usr/sbin`）下**什么都不做**
   —— 路径本已可达；非 usrmerge 且 `/sbin/uci` 缺失时才补软链；若 `/sbin/uci`
   已存在（真实文件，或指向别处的链接）则**一律不覆盖**，只告警（它可能属于
   别的包）。创建或复用链接时写下标记
   `/usr/lib/openclash-rt/.sbin-uci-created`，内容 = 链接指向的目标。
2. **删除侧**：清理点放在 **`prerm`**（`remove|deconfigure` 分支）而不是
   `postrm`。原因：`prerm` 跑在文件被移除**之前**，此时标记还在、凭据可读；
   到了 `postrm` 阶段本包文件已被移除，拿不到凭据，就只剩盲删一条路 —— 而那
   正是要避免的。
3. **删除条件三者同时成立**：标记存在 **且** `/sbin/uci` 是符号链接 **且** 它的
   `readlink` 结果等于标记里记录的目标。任一条不成立就原样留下 —— 用户手工把
   链接改指到别处时也不该被我们删掉。
4. **`postrm purge`** 只负责删掉标记文件本身（它由 `postinst` 写入，**不在 dpkg
   文件清单里**，dpkg 不会清理它），外加一次幂等兜底。

`prerm` 与 `postrm` 里是**同一份** `rm_sbin_uci_if_ours()` 实现，且 `postinst`
与它们共用同一个标记路径字面量 —— 这三处的一致性由
`tests/test_maintainer_scripts.sh` 的 B/C 组逐字节锁死（含一条变异验证：把旧缺陷
注入回去，C 组的"函数体之外不存在 `rm -f /sbin/uci`"必须转红）。

> ⚠️ 同一套策略还有一个**第二落点**：`tests/e2e/linux/run-e2e.sh` 里手工复刻的
> 安装步骤（e2e 不走 dpkg）。它曾经用的也是 `ln -sf` 那个自环形态。两处必须同形，
> 否则 e2e 验证的是一段与生产不同的逻辑、而 postinst 改坏了它还会继续绿着给出
> 虚假安心 —— 该一致性由同一套件的 C9 组断言锁住。

### 2.3 防火墙契约（**本契约最容易静默失败**）

**契约**：存在一个 nftables 表 `table inet fw4`，且它带有若干 base chain。
上游**只往里插规则，从不创建这个表**。

#### 2.3.1 `fw4` 必须在 PATH 上（否则整段分流逻辑被跳过）

`FW4` 变量由三条独立路径设置：

```sh
init.d/openclash:15      FW4=$(command -v fw4)
openclash.sh:27          FW4=$(command -v fw4)
openclash_chnroute.sh:20 FW4=$(command -v fw4)
openclash_watchdog.sh:17 FW4=$(command -v fw4)
```

随后 `init.d/openclash:2040` 用它做**二选一的模式开关**：

```sh
if [ -z "$FW4" ]; then
   # ---- iptables / ipset 路径（400 处 iptables/ipset 调用）----
   if [ "$iptables_compat" -eq 0 ]; then ...
else
   # ---- nft / fw4 路径（356 处 nft 调用）----
fi
```

> ⚠️ **静默降级风险**：如果 `fw4` 不在 PATH 上，`FW4` 为空 → 上游走 **iptables 路径**，
> 于是需要 `ipset`、`-m owner`、`addrtype` 等等。功能"能用"但与我们设计的
> nftables 骨架完全不匹配，且 Debian 上 `ipset` 已进入废弃流程。
>
> **决策：兼容层提供 `fw4`，让上游稳定走 nft 路径。** 理由是 nft 路径只有
> **一个** 外部依赖（`inet fw4` 表），而 iptables 路径有 **四个**
> （iptables / ip6tables / ipset / owner match）。

顺带说明 `init.d/openclash:3567` 的兼容探测：

```sh
iptables_compat=$(iptables -m owner -h 2>/dev/null | grep "owner match options" || command -v fw4 || echo 0)
```

它随后被以**整数**方式使用：`[ "$iptables_compat" -eq 0 ]`（`init.d:2042`）。
在 Debian 上若 `iptables -m owner -h` 成功，该变量是一段**文本**，
`-eq` 比较会报 `integer expression expected` 并判为假——**恰好落到期望的分支**。
这条只影响 iptables 路径，我们走 nft 路径，故无需干预，但需在排障手册中
说明这条无害的 stderr 噪音来源。

#### 2.3.2 兼容层必须**预建**的 base chain（7 个）

**权威依据不是我推断出来的，而是上游自己写出来的。** `init.d/openclash:2921–2927`
的 `revert_firewall()` 逐链清理，直接给出了上游期望存在的链清单：

```sh
if [ -n "$FW4" ]; then
   for nft in "input" "forward" "output" "dstnat" "srcnat" "nat_output" "mangle_prerouting" "mangle_output"; do
      local handles=$(nft -a list chain inet fw4 ${nft} |grep -E "openclash|OpenClash" |awk -F '# handle ' '{print$2}')
      for handle in $handles; do
         nft delete rule inet fw4 ${nft} handle ${handle}
      done
   done
```

其中**只有 7 个**需要兼容层预建：

| chain | `type` | `hook` | `priority` | 上游用法 |
|---|---|---|---|---|
| `input` | filter | input | 0 (`filter`) | `insert rule ... position 0`（ICMP reject、dport 443 reject、dnat 放行） |
| `forward` | filter | forward | 0 (`filter`) | 同上 + `iifname/oifname utun` 计数放行 |
| `output` | filter | output | 0 (`filter`) | `meta mark` 匹配、`utun` 计数 |
| `dstnat` | nat | prerouting | -100 (`dstnat`) | **旁路网关的核心**：`th dport 53 … dnat/redirect` |
| `srcnat` | nat | postrouting | 100 (`srcnat`) | `add rule ... jump openclash_post` |
| `mangle_prerouting` | filter | prerouting | -150 (`mangle`) | 打 mark |
| `mangle_output` | filter | output | -150 (`mangle`) | 本机出流量打 mark |

> ### ⚠️ 第 8 个链 `nat_output` 为什么**不能**由兼容层预建
>
> `revert_firewall` 的清单里有它，但 `set_firewall()` 的 `init.d:1356` **会自己创建它**：
>
> ```sh
> nft 'add chain inet fw4 nat_output { type nat hook output priority -1; }'
> ```
>
> `nat_output` 是一个**带 hook 的基础链**（`type nat hook output priority -1`），
> 承担**本机出流量的 DNAT** —— 即"服务器自身走代理"（`router_self_proxy`）的通路。
>
> 如果兼容层抢先创建一个**没有 hook** 的 `nat_output`，上游的 `add chain` 会因
> "File exists" 失败（该错误被 `set_firewall` 整体的 `>/dev/null 2>&1` 吞掉），
> 结果留下一个**永不求值的空链** → 本机代理静默失效。
>
> **规则：只预建上表 7 个；`nat_output` 交给上游。**
> 这与"在 Debian 上重现 OpenWrt 的 `inet fw4` 表"这一目标并不矛盾——
> fw4 在 OpenWrt 上也不创建 `nat_output`，是 OpenClash 自己建的。

生成的 `nft` 骨架（幂等）：

```
table inet fw4 {
    chain input            { type filter hook input       priority filter;  policy accept; }
    chain forward          { type filter hook forward     priority filter;  policy accept; }
    chain output           { type filter hook output      priority filter;  policy accept; }
    chain dstnat           { type nat    hook prerouting  priority dstnat;   policy accept; }
    chain srcnat           { type nat    hook postrouting priority srcnat;   policy accept; }
    chain mangle_prerouting{ type filter hook prerouting  priority mangle;   policy accept; }
    chain mangle_output    { type filter hook output      priority mangle;   policy accept; }
}
```

**为什么 `policy accept`**：
- OpenWrt 上 fw4 的这三个链是 `policy drop` + 显式 `jump` 到 zone 链。
- 服务器场景下**本机代理 + 旁路网关**不能被 drop 策略误伤（会直接断网、且断 SSH）。
- 上游所有插入都带 `position 0`，即**永远排在链首**，先于任何 accept 规则被评估，
  所以 `policy accept` 不影响 OpenClash 的规则生效，只消除了"误封"风险。
- 需要 masquerade 的场景（NAT 网关模式）由兼容层按配置**追加** `srcnat` 规则，
  默认不追加——旁路网关通常不需要（客户端保留源 IP 回程）。

#### 2.3.3 上游**自己创建**的 chain 与 set（兼容层**不要**预建）

上游会 `nft 'add chain inet fw4 <name>'` 自建（15 个 chain）：

```
openclash              openclash_v6
openclash_output       openclash_output_v6
openclash_post         openclash_post_v6
openclash_mangle       openclash_mangle_v6
openclash_mangle_output  openclash_mangle_output_v6
openclash_dns_redirect openclash_upnp
openclash_wan_input    openclash_wan6_input
nat_output             # ← 注意：带 hook 的 base chain，但由上游自建
```

上游自建的 set：

| set | 类型 | 创建点 |
|---|---|---|
| `localnetwork` | `ipv4_addr; flags interval; auto-merge` | `init.d:1273` |
| `common_ports` | `inet_service; flags interval` | `init.d:1292` |
| `lan_ac_black_ips` / `lan_ac_black_ipv6s` / `lan_ac_black_macs` | v4/v6/ether | `init.d:1234-1240` |

> 这些 set 名（`lan_ac_white_ips` 等）**与 OpenWrt fw4 的命名完全一致**，
> 说明上游是从 fw4 的实现里抄的命名并自行创建。因此兼容层无需也无法"接管"，
> 只要保证表存在、且上游有 CAP_NET_ADMIN 即可。

#### 2.3.4 `fw4` 垫片的命令面

上游只用 `command -v fw4`，从不执行 `fw4 <子命令>`。但 LuCI 层与
`uci-defaults` 可能调用，且排障需要，故垫片提供：

```
fw4 check            # 校验骨架是否完整（幂等断言）
fw4 reload|restart   # 重新断言骨架 + 执行 include 脚本（见 §2.3.5）
fw4 status|print     # nft list table inet fw4
fw4 flush            # 仅删上游 openclash_* 规则后再断言骨架
fw4 stop             # 清空表
fw4 (无参)           # 等价于 check
```

#### 2.3.5 firewall include 契约：`/var/etc/openclash.include`

**这是"防火墙重生"机制**，也是最容易漏掉的一条。`init.d/openclash:1143–1159`：

```sh
if [ -z "$(uci -q get firewall.openclash)" ] || [ -z "$(uci -q get ucitrack.@openclash[-1].init)" ]; then
   uci -q delete ucitrack.@openclash[-1]
   uci -q add ucitrack openclash
   uci -q set ucitrack.@openclash[-1].init=openclash
   uci -q commit ucitrack
   uci -q delete firewall.openclash
   uci -q set firewall.openclash=include      # ← 注册为 fw4 的 include 脚本
   uci -q set firewall.openclash.type=script
   uci -q set firewall.openclash.path=/var/etc/openclash.include
   [ -n "$FW4" ] || uci -q set firewall.openclash.reload=1
   uci -q commit firewall
fi

mkdir -p /var/etc
cat > "/var/etc/openclash.include" <<-EOF
/etc/init.d/openclash reload "firewall"
EOF
```

**语义**：在 OpenWrt 上，fw4 每次 reload 都会执行所有
`firewall.*=include` 且 `type=script` 的脚本。OpenClash 借此保证：
**只要防火墙重载，OpenClash 的 nft 规则就自动重建**（否则宿主机任何
防火墙操作都会把 OpenClash 的规则冲掉，代理静默断开）。

**兼容层的处理（两条都必须做）**：

1. **提供 `/etc/config/firewall`**，使上述 `uci -q get/set firewall.openclash`
   全部成功（否则 `uci set` 在不存在段上会失败，注册不落地）。
2. **`fw4 reload` 必须执行 include 脚本**，与 OpenWrt fw4 行为一致：

   ```sh
   # fw4 垫片 reload 的核心逻辑
   assert_skeleton              # 1) 幂等重建 7 个基础链
   run_includes                 # 2) 遍历 /etc/config/firewall 的 include/script 段并执行
   ```

   `run_includes` 用 `uci show firewall | grep '=include'` 找出段名，
   读 `path` 与 `type`，对 `type=script` 的执行该脚本。
   这样 `/var/etc/openclash.include` → `/etc/init.d/openclash reload firewall`
   的调用链与 OpenWrt **完全一致**。

> ✅ 这条契约让"服务器上任何 `nft flush ruleset` / 防火墙重启都不会让
> OpenClash 失联"这一能力**自动成立**，无需额外守护进程。
> 同时也解释了为什么 `openclash.service` 的 `ExecReload` 是
> `/etc/init.d/openclash reload firewall`——两者是同一个入口。

#### 2.3.6 清理语义：基于 comment 的删除（影响兼容层的规则命名）

`revert_firewall` 用 **comment 匹配** 来定位自己的规则（`init.d:2923`）：

```sh
nft -a list chain inet fw4 ${nft} | grep -E "openclash|OpenClash"
```

并按 handle 删除（`init.d:2929–2935` 同理处理 chain 与 set）：

```sh
for handle in $(nft -a list chains |grep -E "chain openclash|OpenClash" |awk -F '# handle ' '{print$2}'); do
   nft delete chain inet fw4 handle ${handle}
done
for handle in $(nft -a list sets |grep -E "set localnetwork|china_ip|lan_ac_|wan_ac_black_|common_ports" |awk -F '# handle ' '{print$2}'); do
   nft delete set inet fw4 handle ${handle}
done
```

**对兼容层的两条硬约束**：

1. **不得在那 7 个基础链里放带 `openclash` / `OpenClash` 字样的 comment 的规则。**
   否则每次 `openclash stop` 会连带删掉兼容层自己的规则。
   兼容层若需在 `srcnat` 加 masquerade，comment 用
   `openclash-rt base masquerade`（含 `openclash-rt` 但**不含**被 grep 的
   `openclash`／`OpenClash` 作为独立词族——注意 `grep -E "openclash"` 会匹配
   `openclash-rt`！**故必须完全避开该字串，建议用 `ocrt-base-masq`**）。
2. **基础链本身不带 `chain openclash*` 名**，不会被 `list chains` 的清理误删。
   （`nat_output` 也不匹配 `chain openclash`，安全。）

> 这一节说明了"命名"在本项目里不是风格问题而是**正确性问题**。

### 2.4 DNS 契约

上游通过两条独立机制改 DNS，兼容层必须分别适配。

#### 2.4.1 `resolv.conf.auto`（Debian 上不存在，**必须补**）

`init.d/openclash:261–269` 用它们探测"上游真实 DNS"：

```sh
elif [ -s "/tmp/resolv.conf.d/resolv.conf.auto" ] && [ -n "$(grep "nameserver" /tmp/resolv.conf.d/resolv.conf.auto)" ]; then
   uci -q set dhcp.@dnsmasq[0].resolvfile=/tmp/resolv.conf.d/resolv.conf.auto
   uci -q set openclash.config.default_resolvfile=/tmp/resolv.conf.d/resolv.conf.auto
elif [ -s "/tmp/resolv.conf.auto" ] && [ -n "$(grep "nameserver" /tmp/resolv.conf.auto)" ]; then
   ...
else
   uci -q set dhcp.@dnsmasq[0].resolvfile=/tmp/resolv.conf.d/resolv.conf.auto   # ← 默认落到一个不存在的文件
fi
```

- OpenWrt 上这两个文件由 `netifd`/`dnsmasq` 从 DHCP 租约生成（10 + 8 = 18 处引用）。
- Debian 上**两者都不存在** → 上游落到 `else`，把 `resolvfile` 指向一个不存在的文件。

**兼容层做法**：提供一个**镜像守护**，把宿主真实上游 DNS
（`/etc/resolv.conf` 中剔除 `127.0.0.0/8`、`::1` 后的 `nameserver` 行）
写入：

```
/tmp/resolv.conf.auto
/tmp/resolv.conf.d/resolv.conf.auto
```

触发时机：启动时、`/etc/resolv.conf` 变化时（inotify）、以及每次
`openclash restart` 前。这样上游读到的就是**正确的上游 DNS**，
而不是"空文件"或"回环地址导致的 DNS 环"。

> ⚠️ 反过来若让上游把 `resolvfile` 指向 `127.0.0.1`，会形成
> `dnsmasq → 127.0.0.1:7874(mihomo) → 上游` 的自环配置错误。

#### 2.4.2 dnsmasq 集成：用上游自己的推导逻辑指向正确目录

上游改了若干 UCI 值，需要翻译为 Debian dnsmasq 的实际配置。
**实现位置：`runtime/net/dnsmasq-adapter.sh` → `/etc/dnsmasq.d/00-openclash-rt-uci.conf`。**

| 上游写入 | 语义 | Debian 落地 | 本层翻译 |
|---|---|---|---|
| `dhcp.@dnsmasq[0].server`（list） | 上游 DNS 服务器（`set_dnsmasq_server()`，`init.d:81`） | `server=<addr>` | ✅ 逐条展开 |
| `dhcp.@dnsmasq[0].resolvfile` | 上游 resolv 文件 | `resolv-file=<path>` | ✅ |
| `dhcp.@dnsmasq[0].noresolv` | 是否忽略 `/etc/resolv.conf` | `no-resolv` | ✅ 仅在 =1 时输出 |
| `dhcp.@dnsmasq[0].cachesize` | 缓存条数 | `cache-size=<n>` | ✅ |
| `dhcp.@dnsmasq[0].localuse` | 只服务本地网段 | `local-service` | ✅ 仅在 =1 时输出 |
| `dhcp.@dnsmasq[0].filter_aaaa` | AAAA 过滤 | `filter-aaaa` | ✅ 仅在 =1 时输出 |
| `${DNSMASQ_CONF_DIR}/dnsmasq_openclash_*.conf` | **上游直接写文件**（`nftset=`/`ipset=` 语句） | 让 `DNSMASQ_CONF_DIR` 指向 `/etc/dnsmasq.d` | ✅ 见下 |

> 🎯 **翻译范围刻意收窄到上面 6 个选项。** 上游不碰的 dnsmasq 选项
> （`domain`、`local`、`domainneeded`、`expandhosts` …）一律**不翻译**，
> 由 Debian 自己的 `/etc/dnsmasq.conf` 管理。盲目全量翻译会覆盖系统 DNS 策略，
> 属于越界。产物因此是「增量的、可删除的」：删掉该文件即完全回退。
> 这一约束由 `tests/test_dns_prep.sh` 的 D1 用例守住（越界翻译会失败）。

**`DNSMASQ_CONF_DIR` 的推导链**（`init.d:14–23`，回顾 §1.3）：

```sh
DEFAULT_DNSMASQ_CFGID="$(uci -q show "dhcp.@dnsmasq[0]" | awk 'NR==1 {split($0, conf, /[.=]/); print conf[2]}')"
if [ -f "/tmp/etc/dnsmasq.conf.$DEFAULT_DNSMASQ_CFGID" ]; then
   DNSMASQ_CONF_DIR="$(awk -F '=' '/^conf-dir=/ {print $2}' "/tmp/etc/dnsmasq.conf.$DEFAULT_DNSMASQ_CFGID")"
else
   DNSMASQ_CONF_DIR="/tmp/dnsmasq.d"        # ← Debian 上会落到这里，错误
fi
DNSMASQ_CONF_DIR=${DNSMASQ_CONF_DIR%*/}
```

#### ✅ 关键技巧：不要去改这段逻辑，而是喂给它一个文件

上游这段推导本身是"**从 dnsmasq 生成的配置里反查 conf-dir**"——
这是一个**通用**机制，不是 OpenWrt 专用的。所以兼容层只需
**模拟"dnsmasq 生成配置"这一步**，上游就会自己推出正确目录。

**实现位置：`runtime/net/prepare-tmp.sh`（已实现并通过测试）。**

1. `/etc/config/dhcp` 里把 dnsmasq 段**显式命名**，使 `cfgid` 可预测：
   ```
   config dnsmasq 'main'
   ```
   则 `uci -q show dhcp.@dnsmasq[0]` 首行是 `dhcp.main=dnsmasq`，
   `awk` 切出的 `conf[2]` = **`main`**，于是 `cfgid` 恒为 `main`。

   > **为什么必须具名**：若用匿名段，首行是 `dhcp.@dnsmasq[0]=dnsmasq`，
   > `cfgid` 变成字面量 `@dnsmasq[0]`。一旦有别的 `dnsmasq` 段插到前面，
   > 索引就漂移，与**启动时预生成的文件名**失配 → 静默降级。
   > 具名后 `cfgid` 与段顺序完全无关。

2. 兼容层在**每次启动时**（`/tmp` 会在重启后清空）生成：
   ```sh
   mkdir -p /tmp/etc
   printf 'conf-dir=%s\n' /etc/dnsmasq.d > /tmp/etc/dnsmasq.conf.main
   ```

   > ⚠️ **写入值必须是「单目录、无尾斜杠、无通配符」**。上游随后会做
   > `DNSMASQ_CONF_DIR=${DNSMASQ_CONF_DIR%*/}`，它只剥离**尾部**的 `/`：
   >
   > | 写入的 `conf-dir` | 经 `%*/` 后 | 结果 |
   > |---|---|---|
   > | `/etc/dnsmasq.d` | 不变 | ✅ |
   > | `/etc/dnsmasq.d/` | 去掉尾斜杠 | ✅ |
   > | `/etc/dnsmasq.d/,*.conf` | **无法匹配，原样保留** | ❌ 非法目录名 |
   >
   > 因此采用与 OpenWrt 的 dnsmasq 初始化脚本**完全相同**的产物形态。
   > 该行为由 `tests/test_dns_prep.sh` 的 P1 用例守住（含反例断言）。

3. 于是上游推导出 **`DNSMASQ_CONF_DIR=/etc/dnsmasq.d`** ——
   Debian dnsmasq 默认就 `conf-dir=/etc/dnsmasq.d/,*.conf`。
   上游写入的 `dnsmasq_openclash_chnroute*.conf` 直接被真实 dnsmasq 加载。

4. **运行期同步**：上游随时可能改 `dhcp.@dnsmasq[0]` 并 `uci commit dhcp`。
   用 systemd 的 **path 单元**监听 `/etc/config/dhcp` 的修改来触发适配器，
   即可覆盖**所有**写入方（init 脚本、watchdog、Web UI），
   无需去 hook `uci`、也无需替换 dnsmasq 的 init 脚本：
   ```
   packaging/debian/openclash-rt-dnsmasq-sync.path   PathModified=/etc/config/dhcp
   packaging/debian/openclash-rt-dnsmasq-sync.service ExecStart=…/dnsmasq-adapter.sh
   ```

> ⚠️ **卸载安全性（已验证）**：若卸载后 `/etc/dnsmasq.d/00-openclash-rt-uci.conf`
> 残留 `server=127.0.0.1#7874` + `no-resolv`，整机会**彻底失去 DNS**。
> `prerm`／`postrm` 必须清理该文件并重启 dnsmasq。
> 上游 `stop_service` 会调用 `revert_dnsmasq`（`init.d:3751`）还原 UCI，
> 因此 prerm 的顺序是：`stop` → 重跑适配器（此时已无 OpenClash 指令）→ 重启 dnsmasq。

> ✅ **零改动、零猜测**：不 patch 上游、不硬编码 `cfgid`、不需要知道
> uci 会生成什么匿名段名（因为段名由我们指定）。
> 这与 §1.3 用伪 `/etc/openwrt_release` 解锁分支是同一个套路：
> **把上游的"探测"喂成真，而不是把上游的"探测"删掉。**
> 这个套路是本项目最重要的实现范式。

> ⚠️ **`nftset` 支持**：`init.d:86` 探测 `dnsmasq --version | grep 'Compile time options:.* nftset'`，
> 有则用 `nftset=...inet#fw4#...`，无则退化为 `ipset=`。Debian 的 dnsmasq
> 通常**未编译 nftset**，因此默认会走 `ipset` 分支——这与我们"只支持 nft"的
> 决策冲突。**处理方式**：preflight 检测；若 dnsmasq 无 nftset，
> 在显式降级清单中登记。影响面：仅 `china_ip_route_pass` 这条
> "把 DNS 解析结果注入直连集合"的辅助优化，不影响主分流路径。

**契约细节（容易踩坑）**：

```sh

**`utun` 设备契约**：上游用 `ip route list | grep utun` 判断 TUN 就绪
（`init.d:730,737,738`），全文 40 处 `utun`：

```sh

- 因此 mihomo 的 TUN 接口**必须**叫 `utun`（与 OpenWrt 一致），

- `ip -6 rule show | grep 2022` 说明上游使用路由规则优先级 **2022**。
- preflight 必须检查：`[ -c /dev/net/tun ]`、`nft` 可用、`ip` 可用。

### 2.9 网络拓扑契约：`lan_ip` 的推导链（**旁路网关的关键**）

**契约**：存在 `network.lan.ipaddr` 与 `network.lan.device`。

上游取 LAN IP 的代码（`init.d:3527`，`openclash_debug.sh:72`，`openclash_history_get.sh:20`）：

```sh
lan_ip=$(uci -q get network.lan.ipaddr 2>/dev/null | awk -F '/' '{print $1}' | tr -d '\n' \
      || ip address show $(uci -q -p /tmp/state get network.lan.ifname \
                           || uci -q -p /tmp/state get network.lan.device) \
             | grep -w "inet" | grep -Eo 'inet [0-9\.]+' | awk '{print $2}' | head -1 | tr -d '\n' \
      || ip addr show 2>/dev/null | grep -w 'inet' | grep 'global' | grep 'brd' \
             | grep -Eo 'inet [0-9\.]+' | awk '{print $2}' | head -n 1 | tr -d '\n')
```

**好消息**：上游**已经写好三级 Linux 兜底**，即使在 Debian 上不给
`/etc/config/network`，第 3 级 `ip addr show | grep brd` 也能拿到一个 IPv4。

**坏消息（必须处理）**：第 2 级会在 Debian 上**抢先命中且选错网卡**——
因为 `$(uci -q -p /tmp/state get network.lan.ifname …)` 展开为空，
`ip address show` 变成**不带参数的 `ip address show`**，它列出**所有**接口，
随后 `head -1` 取到的往往是 **WAN/上行接口**的地址，而不是 LAN 网关地址。

**`lan_ip` 用在哪**（决定了这不是小事）：

| 用途 | 影响 |
|---|---|
| `localnetwork` nft 集合的元素 | 旁路网关决定"哪些流量算内网、不该被代理" |
| `lan_ac_white_ips` / `lan_ac_black_ips` 的生成 | 客户端白/黑名单匹配 |
| `dstnat` 链里 `ip saddr <lan_cidr>` 的判定范围 | **决定旁路网关到底接管哪些客户端** |
| `intranet_allowed`（允许访问内网）的规则 | 内网直连放行 |

如果 `lan_ip` 取成了 WAN 地址，`localnetwork` 集合与 `dstnat` 的源地址范围
就会**偏掉整个网段**，表现为"部分客户端能上代理、部分不能"这类极难排查的现象。

**兼容层做法**：`.deb` 安装时（`postinst`）探测并写入 `/etc/config/network`：

```
config interface 'lan'
	option device '<LAN_IF>'
	option proto 'static'
	option ipaddr '<LAN_IP>/<PREFIX>'
```

探测策略（按优先级）：
1. 默认路由对应的**上游接口**排除后，取承载私网网段的接口；
2. 或取含 `brd`（broadcast）且不是默认路由出口的第一个全局 IPv4 接口；
3. 或读取安装环境变量 `OPENCLASH_RT_LAN_IF` / `OPENCLASH_RT_LAN_IP` 显式指定。

写入后，第 1 级 `uci -q get network.lan.ipaddr` 直接命中，
与 OpenWrt 行为**完全一致**，且不再依赖第 2/3 级的模糊兜底。

> 这一点在"**纯本机代理**（不涉及旁路）"场景下影响较小，
> 但在用户选定的"**本机代理 + 旁路网关**"场景下是**必做项**。

### 3.1 vendor LuCI 落点（路线 B 的前端布局）

vendor 树来源是 `fetch-luci-vendor.sh`，按 `openwrt-21.02` 分支拉 8 个上游包；
**整棵树原样保留**——下面列出的是打包期把它们"挪进 .deb"时的目标路径，
**而不是修改 vendor 树本身**。这是让 §4"上游同步零阻力"的根本前提。

**唯一事实来源**：见 `scripts/build-deb.sh` 的 §5c 节（实现位置唯一）、
`tests/test_luci_vendor_install.sh`（断言位置唯一）。

**为什么命名空间统一加 `luci/` 前缀**：
上游 4 个包（luci-base / luci-lib-base / luci-compat / luci-theme-bootstrap）
的 `luasrc/*.lua` 都是**扁平**的（`luasrc/cacheloader.lua`、`luasrc/util.lua` 等），
但每个文件都用 `module("luci.X")` 声明自己是 `luci.*` 命名空间。
Lua 5.1 的 `require "luci.cacheloader"` 通过 `package.path` 解析为
`/usr/lib/lua/luci/cacheloader.lua`，所以**所有 4 个包的 luasrc/* 都必须装到
`/usr/lib/lua/luci/` 下**——加 `luci/` 前缀是 Lua 5.1 require 机制决定的，
不是设计选择。这是 P2 唯一不平凡的映射，文档必须显式写出来。

| vendor 路径（**原样**） | `.deb` 内路径 | 用途 / 命名空间 |
|---|---|---|

| `vendor/luci/luci-lib-base/luasrc/*` | `/usr/lib/lua/luci/*` | `luci.{util,http,ltn12,debug}` |

**i18n 路径**：`luci/util.lua:694 libpath()` = `dirname(debug.__file__)`，
debug.lua 落地在 `/usr/lib/lua/luci/debug.lua` ⇒ `libpath()` 返回
`/usr/lib/lua/luci/` ⇒ `luci/i18n.lua:9 i18ndir = libpath() .. "/i18n/"` =
`/usr/lib/lua/luci/i18n/`。**所有 `.lmo` 必须落在该目录下**，文件名是
`<lang>.lmo`（如 `en.lmo`、`zh-cn.lmo`），由上游 `src/po2lmo.c` 编译 `.po` 生成；
上游本身有 30+ 种语言，编译后约 90 个 `.lmo`，每个 30-150 KB。

**两个 acl.d 的取舍**：
- `/usr/share/acl.d/luci-base.json` —— **OpenWrt uhttpd 用**，限制"未登录可匿名调哪些 ubus 方法"。
  我们的路线 B **不走 uhttpd**（P3 自研 HTTP 宿主），**此目录暂不消费**。
- `/usr/share/rpcd/acl.d/luci-base.json` —— **rpcd 直接读**，授权规则按"用户/组"分。
  **必须安装**，因为 rpcd 启动时会读此目录决定 ACL。包装未构建的 rpcd 启动时会
  因"找不到 ACL 默认策略"而拒绝所有 RPC，这是 P3 之前最容易踩到的坑。

**uploads 目录特殊处理**：`/etc/luci-uploads/` 在 Debian 上**原本不存在**，
但 `luci-base/acl.d` 里写了 `cgi-io.write` 的 `"/etc/luci-uploads/*"` 通配符。
为避免 ACL 规则指向不存在的目录造成 rpcd 拒绝服务，**目录占位文件
`.placeholder` 必须落地**。

**为什么不一次性安装全部**：
按"依赖图谱 + 单一事实来源"分四批：
1. **本批（P2-A）**：上表全部 `cp -a` + shebang 钉定 + 占位文件 + acl.d/menu.d 落位。
2. **P2-B**（下一批）：po2lmo 构建脚本 + .lmo 生成 + i18n 实测。
3. **P3**：HTTP 宿主 + `/etc/config/uhttpd` 注入 + `/etc/init.d/uhttpd`。
4. **P4**：执行上游 `uci-defaults` + `ucitrack` 触发 + 105 个端点接通。

每批都能在本机上做**静态分析 + 行为验证**，不需要等完整环境。

> ⚠️ 最后两行是**运行时创建**的，**不在 dpkg 文件清单里** —— dpkg 既不会在升级时
> 覆盖它们，也不会在卸载时删除它们。凡由维护者脚本创建的路径都必须自带清理逻辑，
> 否则会永久残留（`/sbin/uci` 的清理还多一层所有权判定，见 §2.2.1）。

**"启动时生成"的路径**（`/tmp` 会在重启后清空）由
`openclash.service` 的 `ExecStartPre` 统一补齐。实际执行顺序为：

```
ExecStartPre=/usr/lib/openclash-rt/prepare-tmp.sh   # 易失路径 + UCI→dnsmasq 翻译
ExecStartPre=-/usr/sbin/fw4 check                   # table inet fw4 + 7 个基础链（§2.3.2）
ExecStart   =/etc/init.d/openclash boot
```

> `fw4 check` 前置可省略失败（`-` 前缀）：nftables 未安装时不应阻断服务启动，
> 但此时上游会因 `command -v fw4` 成功而仍走 nft 路径并在插入规则时失败——
> 因此 `postinst` 会显式给出告警。

**依赖（`Depends`）**（与 `packaging/debian/control` 保持一致）：
`bash, coreutils, findutils, grep, sed, gawk, curl, ca-certificates, unzip,
ruby, iproute2, procps, sysvinit-utils, cron, nftables, dnsmasq, libc6`。
`Recommends`：`kmod, ipset, iputils-ping, bind9-dnsutils, socat`。

### 3.2 vendor LuCI i18n 编译（.po -> .lmo）

#### 3.2.1 为什么需要这步
上游 `libtemplate.so` 把翻译表存在 `.lmo` 二进制里（紧凑、二进制 grep），由
`tparser.load_catalog(lang, dir)` 读取。Lua 端没有 reload 接口，**必须**打包时
把 `.po` 编译成 `.lmo`，运行时只读不写。

#### 3.2.2 落位契约

| 源路径 | 落位 |
|---|---|
| `vendor/luci/<pkg>/po/<lang>/base.po` | `/usr/lib/lua/luci/i18n/<pkg>.<lang>.lmo` |

- 路径模板：`/usr/lib/lua/luci/i18n/<pkg>.<lang>.lmo`
- 命名匹配：`fnmatch("*.<lang>.lmo", name, 0)` —— `<pkg>` 部分是 `*` 通配的"任意"
- 多包共存互不覆盖：`luci-base.zh-cn.lmo` / `luci-compat.zh-cn.lmo` / `bootstrap.zh-cn.lmo` 各占一位

#### 3.2.3 i18ndir 为什么唯一
`vendor/luci/luci-base/luasrc/i18n.lua:13`：
```lua
i18ndir = util.libpath() .. "/i18n/"
```
而 `util.libpath()` 实现：
```lua
function libpath()
    return require "nixio.fs".dirname(ldebug.__file__)
end
```
`ldebug.__file__` 指向 `luci.debug` 模块的物理位置（来自 `luci-lib-base/luasrc/debug.lua`），
而我们的 §3.1 把 `luci-lib-base/luasrc/*` 平铺到 `/usr/lib/lua/luci/` 下，
故 `i18ndir` 唯一 = `/usr/lib/lua/luci/i18n/`，**所有** .lmo 都进这里。

#### 3.2.4 编译命令（po2lmo）
- **二进制**：`po2lmo`（编译自 `vendor/luci/luci-base/src/po2lmo.c`）
- **依赖**：`<stdint.h> <stdio.h> <fnmatch.h> <stdlib.h> <string.h>` —— 纯 libc
- **编译**：`cc -O2 -Wall -o po2lmo po2lmo.c`（**不** link template_lmo.c，
  **不**需 lemon/flex/bison —— po2lmo.c 只引用 `lmo_entry_t` 结构体定义）
- **调用**：`po2lmo <input.po> <output.lmo>`
- **副作用**：空 .po（无消息）会 `unlink` 输出文件，由脚本 warn 而非 fail

#### 3.2.5 卫生
- `.po` 源**不**入 staging（编译产物才是 .lmo）
- `.y` / `.c` / `.h` 不入 staging（编译期材料）
- `po2lmo` 二进制**不**入 deb（属于 `build/`，由 build-deb.sh §4 清）

#### 验收（§3.2 — i18n 编译）

```sh
# 1) .lmo 文件至少 2 个（英文必须有；语言数取决于 vendor）
find /usr/lib/lua/luci/i18n -name '*.lmo' | wc -l           # 应 ≥ 1

# 2) 命名约定抽查（任意一个 .lmo 都应匹配 <pkg>.<lang>.lmo）
find /usr/lib/lua/luci/i18n -name '*.lmo' -printf '%f\n' | head -1   # luci-base.en.lmo 或同类

# 3) po2lmo 二进制不存在（属于 build/，§4 已清）
command -v /usr/lib/openclash-rt/build/po2lmo               # 应 fail

# 4) i18ndir 不污染 .po / .y / .c / .h
find /usr/lib/lua/luci -name '*.po' -o -name '*.y' -o -name '*.c' -o -name '*.h' | wc -l   # 应 = 0
```

dpkg -r openclash-rt && {
    test -f /etc/dnsmasq.d/00-openclash-rt-uci.conf \
        && echo "FAIL 卸载后仍有 dnsmasq 劫持残留（会导致整机断网）"
    systemctl is-active dnsmasq >/dev/null && echo "dnsmasq 仍在运行（应有 DNS）"
    getent hosts deb.debian.org >/dev/null && echo "OK 卸载后 DNS 正常" \
        || echo "FAIL 卸载后 DNS 不可用"
}

# --- §2.5 进程探测 ---
command -v pidof
test -c /dev/net/tun
command -v nft
test -L /etc/openclash/clash -o ! -e /etc/openclash/clash   # 软链由上游创建

# --- §2.6 定时任务 ---
test -d /etc/crontabs
command -v crontab

# --- §2.8 内核模块探测 ---
command -v lsmod
command -v gawk
```

以上检查中 §2.3.5／§2.4 的 `/tmp/*` 项在**未启动过 OpenClash 时**可能为空，
故 `run-e2e.sh` 分为 **Stage 1（安装后静态检查）** 与
**Stage 2（`openclash start` 后检查）** 两段。

## 5. 契约变更管理

上游每次同步（`scripts/sync-upstream.sh`）后，**必须重跑附录 A 的测绘**
并与本文的表格逐项比对。新增/变更的绝对路径即为**新的契约项**，
意味着兼容层可能要新增一个路径或一个设施。

`sync-upstream.sh` 的冲突告警（`exit 2` + GitHub Issue）覆盖的是
`patches/*.patch` 的应用失败；**契约漂移是另一类风险**，
需要在 CI 中加一道"契约快照比对"（见 `tests/e2e/linux/run-e2e.sh` 的
`--contract-check` 模式）。

## 附录 A：测绘方法（可复现）

下列命令在 `upstream/luci-app-openclash/root` 下执行，产出本文所有数字。

```sh
# A1  硬编码绝对路径频次（按目录聚合）
grep -rhoE '/(etc|usr|lib|sbin|bin|var|opt|run|tmp)/[A-Za-z0-9_./-]*' \
     --include='*.sh' --include='openclash' --include='*.lua' . \
  | sed -E 's/\$\{?[A-Za-z_][A-Za-z0-9_]*\}?/<V>/g' \
  | sort | uniq -c | sort -rn

# A2  source/. 的绝对路径（路径契约主体）
grep -rnE '^[[:space:]]*(source|\.)[[:space:]]+/' \
     --include='*.sh' --include='openclash' .

# A3  inet fw4 表与 chain 清单
grep -rhoE 'inet fw4 [a-zA-Z0-9_]+' --include='*.sh' --include='openclash' . \
  | sed 's/^inet fw4 //' | sort | uniq -c | sort -rn

# A4  哪些 chain 是上游自建的（兼容层不要预建）
grep -rhoE "nft[^\"']*add chain inet fw4 [a-zA-Z0-9_]+" \
     --include='*.sh' --include='openclash' . | sort -u

# A5  FW4 模式开关
grep -rn 'command -v fw4\|-z "$FW4"' --include='*.sh' --include='openclash' .

# A6  procd API 面
grep -rnE '\bprocd_(open|close|set_param|append_param|running|kill|send_signal)' \
     --include='*.sh' --include='openclash' .

# A7  进程/设备探测
grep -rnE '\bpidof\b|\butun\b' --include='*.sh' --include='openclash' .

# A8  包管理器自更新
grep -rnE '/bin/opkg|/usr/bin/apk|\.ipk|\.apk' --include='*.sh' --include='openclash' .

# A9  涉及的 UCI 包（§2.2）
grep -rhoE "uci[^\n]{0,60}" --include='*.sh' --include='openclash' . \
  | grep -oE '"[a-z_@][a-zA-Z0-9_.@\[\]-]*"' | tr -d '"' \
  | cut -d. -f1 | sort -u

# A10 fw4 include 契约与 lan_ip 推导（§2.3.5 / §2.9）
grep -rn 'firewall.openclash\|ucitrack\.\|openclash.include' --include='*.sh' --include='openclash' .
grep -rn 'network.lan' --include='*.sh' --include='openclash' .

# A11 上游自己声明的 fw4 链清单（§2.3.2 的权威来源）
grep -n 'for nft in "input"' -A 6 etc/init.d/openclash
```
