# OpenClash 移植到 Debian/Ubuntu 无桌面服务器 —— 可行性分析报告

> 分析对象：`https://github.com/vernesong/OpenClash`
> 分析版本：`master` @ `0.47.156`（2026-08-10，活跃维护中）
> 分析方法：完整拉取源码（23 MB / 274 文件），逐文件量化 OpenWrt 专有依赖，逐 API 分析前后端耦合
> 结论日期：2026-10-01

---

## 一、总体结论

**结论：可行（绿灯），但必须放弃"移植"这个词。**

本项目真正的形态是：

> **构建一套「OpenWrt 兼容运行时」，让上游 OpenClash 代码以零修改（或极少 patch）的方式在 Debian/Ubuntu 上原样运行，再配一个适配服务器语义的 Web UI 与网络层。**

这个形态有一个决定性优势：**它能同时满足你的两个硬需求** ——
- 「100% 复刻」：不是重写功能，而是同一份代码在跑
- 「上游同步更新」：`git pull` 上游即可，兼容层不用跟着改

反过来，如果走"读 OpenClash 源码 → 在 Debian 上重写一遍"的路线，这两条需求都会直接崩掉：重写必然产生行为差异，且上游每次更新都要人工追平。

### 三条结论性判断

| 判断 | 结论 | 置信度 |
|------|------|--------|
| Debian/Ubuntu 上能否跑 OpenClash 后端 shell 逻辑 | **能，且约 70% 代码零改动** | 高 |
| 能否让上游脚本零修改运行 | **能，靠 UCI/procd/fw4/dnsmasq 四个兼容垫片** | 高 |
| 前端 LuCI 能否在 Debian 上复用 | **能复用绝大部分，但必须先搭 LuCI 运行时** | 中高 |
| 拦截层（透明代理）是否需要 OpenWrt | **不需要，mihomo 原生支持 Linux TUN/auto-route** | 高 |
| 上游持续同步是否可持续 | **可持续，但需 CI 做 patch 冲突检测** | 中高 |

**关键读数：**

1. **`uci` 出现 157 次，但其中绝大多数是"读配置"**。上游已经把 UCI 访问封装在 `usr/share/openclash/uci.sh` 的 `uci_get_config()` 里。**只要 Debian 上有一个能跑的 `uci` 二进制，这 157 处全部零改动。**
2. **`procd` 只出现 21 次，且集中在 `init.d/openclash` 的 `start_service()` / `stop_service()` / `start_watchdog()` 三个函数中**。映射到 systemd 只需写一个单元文件 + 20 行 `procd_*` shim 函数。这是最容易被高估的难点，实际成本极低。
3. **防火墙是唯一的重量级耦合**：`set_firewall()` / `revert_firewall()` / `firewall_lan_ac_traffic()` 三个函数约 2,000 行，占 `init.d/openclash` 的一半，925 处 `nft`/`iptables`/`ipset` 调用几乎全在这里。
4. **约 9,000 行（后端 54%）是纯配置处理逻辑** —— YAML 生成/改写、订阅解析、节点/规则/策略组编辑、GEO 下载。这些代码完全不碰 OpenWrt，是"白送"的资产。

**关键结论：**

- **视图层（18,832 行）不用 LuCI 的 JS 框架，只用裸 XHR + 105 个 JSON 端点。** 这意味着这些页面本质上就是"一组标准 HTML+JS 静态页 + 一个 JSON API"，换掉后端运行时它们照样能跑。

上游 GitHub Actions（`.github/workflows/compile_meta_core.yml`）编译的内核矩阵包含：

linux-mips/le/mips64/le  linux-riscv64  linux-s390x  linux-loong64

**`linux-amd64` 与 `linux-arm64` 均在列**，正好覆盖 Debian/Ubuntu 服务器的主流架构。内核下载路径为 `raw.githubusercontent.com/vernesong/OpenClash/core/<branch>/meta/clash-linux-<arch>.tar.gz`，服务器环境可直接复用（需注意 GitHub 可达性，上游自带 CDN 加速选项）。

## 三、真正的技术难点（不是"能不能"，而是"改多少细节"）

### 难点 1：`set_firewall()` 依赖 OpenWrt 的 `inet fw4` 表结构 ⭐⭐⭐⭐⭐

上游在 Debian 上跑时，`command -v fw4` 会返回空，于是走 **fw3（iptables + ipset）分支**。而 OpenWrt 的 iptables 与 Debian 的 iptables 语法基本一致，但：

- 上游用 `ipset` 管理 `china_ip_route`、`lan_ac_black_ips` 等集合
- 上游的规则插入依赖 OpenWrt `fw3` 的链已存在（`openclash`、`openclash_post`、`openclash_output`）
- `uci -q get firewall.openclash` 那一段（自建 firewall include）在 Debian 上无意义

**解决思路（推荐）：在 Debian 上"托管"一个假的 `inet fw4` 表。**
即由兼容层负责 `nft add table inet fw4`，并按 OpenWrt fw4 的语义建立 base chain（`prerouting`/`output`/`forward` + 正确的 hook priority/type），并预建 `openclash*` 链。做完这层之后，上游那 925 处 `nft insert rule inet fw4 openclash ...` **一行都不用改**。

**备选思路**：走 fw3/iptables 分支，写 ipset + iptables 的 Debian 适配（Debian 默认已装 `iptables`/`ipset`，成本也不高，但与上游未来可能弃用 fw3 的方向相悖）。

### 难点 2：dnsmasq 集成方式不同 ⭐⭐⭐

OpenWrt 通过 UCI 管理 dnsmasq（`/etc/config/dhcp` 的 `dnsmasq` section），上游的 `change_dnsmasq()` / `revert_dnsmasq()` 直接改 UCI 并重载。Debian 的 dnsmasq 用 `/etc/dnsmasq.d/*.conf` + systemd。

需要写一层适配：把上游生成的 `conf-dir` / `server=` / `ipset=` / `nftset=` 配置块落到 Debian 的 dnsmasq 配置目录，并重写重启逻辑。

**注意**：上游**强制要求 `dnsmasq-full`**（含 `ipset`/`nftset` 编译选项），Debian 的 `dnsmasq` 包默认就带这些，这点反而比 OpenWrt 省事。另一个方向是让 mihomo 内置 DNS 直接接管 53 端口，绕过 dnsmasq —— 需要评估功能覆盖度。

### 难点 3：服务器语义与路由器语义的差异 ⭐⭐⭐

OpenClash 的功能模型建立在"这是一台路由器"之上。在 Debian/Ubuntu 服务器上需要重新定义：

| OpenClash 功能 | 服务器上的对应 | 处理方式 |
|----------------|----------------|----------|
| WAN/LAN 双接口模型 | 单网卡或旁路由/网关 | 重写 `openclash_get_network.lua` 的 WAN 探测 |
| DHCP 租约列表、局域网设备管理 | 无（除非装 dnsmasq/isc-dhcp） | 装 dnsmasq 后可用；否则置空 |
| 无线相关 | 服务器无 | 上游本来就没有无线功能，无影响 |
| UPnP 排除（`upnp_exclude`） | 需装 `miniupnpd` | 可选降级 |
| `opkg`/`apk` 装依赖、IPK 插件自更新 | `apt` | `openclash_update.sh` 里 71 处需适配/禁用 |
| 内核模块检查 `check_mod()` | Debian 模块名不同 | 上游已有 **容器检测短路**逻辑，可扩展为"非 OpenWrt 直接放行" |
| 固件/路由器型号展示 | `dpkg`/`uname` | `uci-defaults` 里读 `/etc/openwrt_release` 需替换 |

### 难点 4：LuCI 运行时需要自建 ⭐⭐⭐⭐

LuCI 不能在 Debian 上开箱运行，缺的是这几层（**但每一层都有现成方案**）：

| 组件 | 状态 | 来源 |
|------|------|------|
| `libubox` + `uci`（含 C 库与 CLI） | ✅ 可在 Debian 编译 | OpenWrt 官方文档明确支持 `cmake && make install` |
| `ubus` / `ubusd` | ✅ 已有 Ubuntu PPA | `ppa:stokito/openwrt`（yurt-page/openwrt-ubuntu） |
| `rpcd` / `jshn` / `jsonpath` | ✅ 同上 | 同上 |
| `uhttpd`（含 ubus 插件） | ✅ 同上 | 同上 |
| `luci-base`（纯 Lua 部分） | ✅ 纯 Lua，可直接安装 | 从 OpenWrt 源码取 `luci/libs/*` |
| `nixio` | ✅ C 模块，Debian 编译无痛 | 上游 luci-lib-nixio |
| `luci-lib-ip` / `luci-lib-jsonc` | ✅ 小 C 模块 | 同上 |
| **`netifd`** | ❌ 不可用 | — |
| **`procd`** | ❌ 不可用 | — |

`netifd` + `procd` 两个缺失项 → 用**自研 shim** 补上（`procd_*` shell 函数映射到 systemd；network 模型用 `ip` 命令实现）。对 OpenClash 而言，`netifd` 只被引用 1 处，`procd` 只有 21 处，**shim 的规模是可控的**。

另外有两条现成的重要先例可参考学习：
- **`lisaac/luci-in-docker`** —— 在 Alpine 容器里跑 LuCI 21.02，**主动移除了 ubus**，证明 LuCI 的 Lua 层可以脱离 ubus 运行
- **`yurt-page/openwrt-ubuntu`（PPA）** —— 已在 Ubuntu 上跑通 `ubus + rpcd + uhttpd` 组合（`uhttpd -f -h /www -p 80 -u /ubus`）

## 四、推荐架构

三层结构，**上游代码零修改**是设计红线：

```
┌──────────────────────────────────────────────────────────────────────┐
│  L1  上游零修改层（git submodule / CI daily sync）                    │
│      luci-app-openclash/                                            │
│        ├─ root/etc/init.d/openclash          (3848 行，原样)          │
│        ├─ root/usr/share/openclash/*.sh,lua,rb (9198 行，原样)        │
│        ├─ luasrc/controller|model|view/      (31272 行，原样)         │
│        └─ root/www/luci-static/              (8592 行，原样)          │
│      ↑ 仅在「patch/」目录放 4~6 个必需补丁，CI 自动 rebase + 冲突告警   │
├──────────────────────────────────────────────────────────────────────┤
│  L2  OpenWrt 兼容运行时（本项目新建，唯一的自研部分）                  │
│                                                                      │
│  ① 配置层   libubox + uci 二进制（glibc 编译）                        │
│  ② 脚本层   /lib/functions.sh、/lib/functions/network.sh  → vendor   │
│  ③ 服务层   rc.common + procd_* 函数 → systemd 适配（~300 行）        │
│  ④ 防火墙   inet fw4 表托管器 + openclash* 链预建（~500 行）          │
│  ⑤ DNS      dnsmasq UCI→/etc/dnsmasq.d 适配（~300 行）                │
│  ⑥ 包管理   opkg/apk → apt 兼容 shim（~100 行）                       │
│  ⑦ 网络     openclash_get_network.lua 的 ip 命令替代版（~200 行）      │
│  ⑧ Web      LuCI Lua 运行时（luci-base + nixio + libuci-lua）          │
│             + HTTP→action 路由器（105 个端点，~800 行）                │
├──────────────────────────────────────────────────────────────────────┤
│  L3  Debian / Ubuntu 系统层                                          │
│      systemd · nftables/iptables · iproute2 · dnsmasq · mihomo core   │
└──────────────────────────────────────────────────────────────────────┘
```

### 「上游同步更新」的机制设计

这是本方案能否长期成立的关键。三条纪律：

1. **只"提供环境"，不"改源码"** —— 90% 以上的适配都在 L2，L1 保持 upstream 原样。
2. **必需的 patch 单独成文件**，放在 `layer1-vendor/patches/`，每个 patch 附一段"patch 理由 + 上游哪次提交可能冲突"的说明。CI 每天拉取上游 → 尝试 apply → 失败立即告警（而不是静默漂移）。
3. **CI 需要一个"行为基线"** —— 用上游官方 267 KB 功能手册（已归档至 `reference/openclash-user-guide.md`）里的防火墙链结构、依赖清单、模式表做验收断言。上游改了行为，CI 必须能发现。

### 已识别的候选 patch 点（预计 4~6 处）

| 文件 | 原因 | 可否避免 |
|------|------|----------|
| `usr/share/openclash/openclash_get_network.lua` | 依赖 `luci.model.network` + netifd | 可用运行时 shim 替代（写一个同名 luci 模块），**可能不需 patch** |
| `etc/uci-defaults/luci-openclash` | 读 `/etc/openwrt_release` 判断架构 | 兼容层预置一个伪造的 `/etc/openwrt_release` 即可，**不需 patch** |
| `etc/init.d/openclash` 顶部 `[ -f /etc/openwrt_release ]` 门控 | 该门控会**跳过整个 dnsmasq 配置目录探测** | 兼容层提供 `/etc/openwrt_release` + 托管 `/tmp/etc/dnsmasq.conf.*`，**可能不需 patch** |
| `usr/share/openclash/openclash_update.sh` | `opkg`/`apk` 装包 | shim 提供假 `opkg`/`apk`，或 patch 掉自动装包 |
| `etc/init.d/openclash` `check_mod()` | 内核模块名 | 扩展容器短路逻辑为"非 OpenWrt 放行" |

**值得注意的设计红利**：上游的 `container()` 检测函数在识别到 Docker/LXC 环境时会**直接跳过内核模块检查**。这意味着上游作者已经为非标准环境留了口子。类似的"兼容性缝隙"越多，需要的 patch 就越少 —— 这是继续深挖源码时优先寻找的东西。

## 五、Web UI 的三条路线对比

前端是整个项目最大的不确定性，因为"复刻"的标准直接决定了成本。

### 路线 A：完整移植 LuCI 运行时（推荐 ⭐）

**做法**：在 Debian 上装 `libubox + uci + ubus + rpcd + uhttpd + luci-base(纯 Lua) + nixio`，自研 `procd`/`netifd` shim，然后**直接使用上游的 `luasrc/` 与 `root/www/`**。

| 维度 | 评价 |
|------|------|
| 复刻度 | ★★★★★ 页面 1:1，交互 1:1，翻译 1:1 |
| UI 重写量 | **接近 0**（18,832 行 htm + 12,275 行 Lua 都可复用） |
| 工作量 | 集中在搭运行时 + 105 个端点路由 + 2 个 shim |
| 上游同步 | ★★★★★ 前端跟着 upstream 走，不用维护 |
| 风险 | 中：LuCI 生态在 Debian 上的长期可维护性；uhttpd/rpcd 属外部 PPA |
| 适用 | **目标就是"100% 复刻"** |

### 路线 B：保留视图，替换 Web 后端

**做法**：不要 uhttpd/rpcd/ubus。写一个轻量 HTTP 服务（Go/Python/Node），做三件事：
1. 用一个小模板引擎渲染 `.htm`（只需实现 `<%:...%>` i18n、`build_url()`、`plugin_version` 等约 350 处插值）
2. 把 105 个 `call()` action 实现为 JSON 端点 —— 内部仍是 `exec shell 脚本 + 读 UCI + 读写文件`
3. 静态文件托管 zashboard / metacubexd（它们本来就只跟 Clash API 说话，零改动）

| 维度 | 评价 |
|------|------|
| 复刻度 | ★★★★☆ 页面几乎 1:1；CBI 表单页（4 个）需改写 |
| UI 重写量 | 小（视图保留；控制器逻辑若用 Lua 运行则可复用，若重写则约 6,600 行） |
| 工作量 | 中：模板引擎 + 105 端点 + 4 个 CBI 页面 |
| 上游同步 | ★★★☆☆ 视图能同步，但控制器逻辑分叉了 |
| 风险 | 低（依赖少、可控） |
| 适用 | 想要最少的外部依赖 |

### 路线 C：全新前端

**做法**：只复用后端，前端用 Vue/React 重写。

| 维度 | 评价 |
|------|------|
| 复刻度 | ★★☆☆☆ 功能可对齐，"复刻"名不副实 |
| 工作量 | **最大**：29 个视图 / 18,832 行的信息密度要重新设计 |
| 上游同步 | ★☆☆☆☆ 前端永久分叉，上游每次加功能都要人工追 |
| 适用 | 只有当"服务器 UI 体验"优先级远高于"复刻"时才选 |

### 关键洞察

**上游视图层不用 LuCI JS 框架、只用裸 XHR —— 这个事实把路线 A 从"理论上可行"拉到了"工程上划算"。** 如果 OpenClash 的页面是用 `L.uci`/`L.ui` 深度绑定的，路线 A 的成本会高得多。现在的实际情况是：**UI 是可搬运的资产，不是需要重写的负债。**

## 六、工作量与风险

### 分阶段（复杂度标注，不给虚假精度）

| 阶段 | 内容 | 复杂度 | 关键交付 |
|------|------|--------|----------|
| **P0 打通壳** | `uci` 二进制编译、`/lib/functions.sh` vendor、`procd→systemd` shim、让 `init.d/openclash start/stop` 在 Debian 上不报错 | 中 | **能 start/stop 的 PoC** |
| **P1 内核跑通** | mihomo core 下载/架构适配、TUN 模式、`/etc/config/openclash` 生效 | 中 | 服务器本机可代理 |
| **P2 拦截层** | `inet fw4` 表托管 + openclash 链预建 + TProxy/Redirect 三模式验证 + IPv6 | **高** | 透明网关可用 |
| **P3 DNS** | dnsmasq 适配层、DNS 劫持、fake-ip/redir-host、chnroute 旁路 | 中高 | DNS 不泄漏、分流正确 |
| **P4 Web 运行时** | LuCI Lua 栈安装、uhttpd/rpcd 或自研服务、105 端点路由 | 高 | 浏览器能打开 OpenClash 页面 |
| **P5 服务器语义收尾** | 网络探测重写、包管理 shim、无 LAN/DHCP 场景降级、state 展示 | 中 | 功能全绿 |
| **P6 工程化** | .deb 打包、CI 上游同步 + patch 冲突检测、行为基线回归、文档 | 中 | 可长期维护 |

**P0→P1 是"两周内能看到东西"的里程碑**，也是最该先做的验证。P2 和 P4 是两个真正吃时间的模块。

### 风险登记

| 风险 | 等级 | 说明 | 缓解 |
|------|------|------|------|
| 防火墙 2,000 行规则的细节遗漏 | **高** | IPv4/IPv6 × 3 模式 × 黑白名单 × chnroute/UPnP 组合爆炸，漏一条就出现"部分设备/部分协议不走代理" | 用上游手册里的链结构逐条对账；写自动化对比脚本（OpenWrt 与 Debian 上 `nft list ruleset` 差异比对） |
| `inet fw4` 托管与宿主防火墙冲突 | 中高 | 若服务器本身跑 firewalld/ufw/docker，钩子优先级会打架 | 用独立 table + 明确的 hook priority；文档写清"不要同时开 ufw" |
| LuCI 运行时在 Debian 的长期可维护性 | 中 | `ubus`/`rpcd`/`uhttpd` 依赖第三方 PPA，非官方支持 | 备选路线 B；或把 ubus/rpcd 也纳入自己的构建流水线 |
| 上游大版本重构导致 patch 全废 | 中 | 上游更新频繁（0.47.x 每周多次） | L2 尽量"提供环境"而非"改源码"；CI 每日同步 + 冲突告警 |
| 上游脚本依赖 BusyBox 特有行为 | 中低 | 上游在 BusyBox ash 下开发，Debian 是 bash/dash，`sed`/`awk`/`date` 参数差异 | P0 阶段就要跑通全量脚本，用 shellcheck + 实际执行覆盖 |
| 无桌面服务器上没有 `/tmp` 可执行权限等 | 低 | systemd 服务器 `/tmp` 常挂 `noexec`，而 OpenClash 把 core 放 `/tmp/etc/openclash/` | 检测并回退到 `/var/lib/openclash` |
| GitHub 不可达导致内核/订阅下载失败 | 低 | 上游自带 CDN 选项 | 支持离线投放内核与配置 |
| "100% 复刻" 的定义漂移 | 中 | 服务器没有 LAN/DHCP/无线，某些路由器功能天然无对应物，容易在中途反复 | **现在就定义清楚验收清单**（见下） |

### 一个必须先定的事："100% 复刻"的验收口径

这是整个项目最容易翻车的地方。建议明确划成三类，写进验收清单：

1. **必须 1:1**：全部 `init.d/openclash` 配置项、三种运行模式（Redir-Host / Fake-IP / TUN）及其 mix 变体、订阅管理、节点/策略组/规则编辑、覆写模块、GEO 管理、DNS 策略、黑白名单、流媒体解锁检测、日志与诊断、zashboard/metacubexd/yacd 集成 —— **即所有与"代理"相关的功能**。
2. **可适配**：设备列表（依赖 dnsmasq 租约）、系统状态展示、内核/模块检查。
3. **明确降级**：IPK/APK 插件自更新、固件升级、无线相关、路由器型号识别 —— 在服务器上无意义或需替换为 `apt`/`dpkg`。

## 八、结论与下一步

### 可行性判定

**可行。** 且存在一条"高复刻度 + 低上游同步成本"的路径。

支撑这个判断的最强证据不是"OpenClash 有多简单"，而是**上游的耦合是高度集中的**：

- OpenWrt 专有依赖的 **85% 集中在 1 个文件**（`init.d/openclash`），而其中的 **80% 又集中在防火墙函数**里
- 后端 54% 的代码是**完全不碰 OpenWrt 的纯逻辑**
- 前端**不用 LuCI JS 框架**，控制器只依赖可移植的纯 Lua + 通用 C 模块
- `procd` 21 处、`luci.model.network` 1 处 —— 这两个被普遍认为的"死结"，实际体量小到可以做 shim

### 建议的推进顺序

1. **先做 P0 + P1 的 PoC**（打通壳 + 内核跑通 TUN），用最小代价证伪最关键的两个假设：`uci` 二进制能不能让上游脚本零改动跑起来、`procd→systemd` shim 够不够用。
2. PoC 成功后**立刻做 P4 的可行性验证**（在 Debian 上把 LuCI Lua 栈 + 一个端点跑通），因为路线 A/B 的选择决定了整个前端工作量，越早定越好。
3. P2（防火墙）留到最后集中攻坚，它是唯一的"高风险高工作量"模块，且必须在 P0/P1 的环境就绪之后才有意义。
4. P6 的 CI 上游同步从第一天就建起来 —— 不要等到最后。

### 需要你拍板的几个问题

1. **目标场景**：服务器是当**本机代理**、**旁路网关**，还是**主路由/网关**？这直接决定 P2 拦截层的工作量与哪些功能可以降级。
2. **前端路线**：A（移植 LuCI 运行时，复刻度最高）、B（保留视图+自研 Web 后端，依赖最少）、还是 C（全新前端）？
3. **部署形态**：原生 `.deb` 包，还是 Docker 镜像？（会显著影响 L2 兼容层的实现方式，尤其防火墙与 systemd 部分）
4. **验收口径**：是否认可以上"必须 1:1 / 可适配 / 明确降级"的三分类？特别是"IPK 插件自更新"这类在服务器上无意义的功能，是否同意降级？
5. **上游同步频率**：每日自动同步 + 冲突告警，还是按版本手动升级？
