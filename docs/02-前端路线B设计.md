# 02 · 前端路线 B 设计：LuCI 兼容宿主

> **状态**：架构已定型（含一轮推翻重做），本文件是前端部分的权威设计。
> **前置**：`docs/01-可行性分析.md`（可行性）、`docs/03-路径契约.md`（后端路径契约）。
> **本文所有结论都有一手证据**，证据的复现命令见 §11。

---

## 0. 一句话结论

前端不做「重写」，也不做「移植 LuCI 到服务器」。

**做法是：把上游的 LuCI 与 OpenClash 前端**原样**装进 Debian，然后只写一层「宿主兼容层」——
它提供 CGI 环境、Lua 5.1 运行时、`nixio`/`uci`/`lucihttp` 的本地实现，以及一个替代 rpcd
的**进程内 session 模块**。上游 39,699 行前端代码零修改。**

## 1. 架构决策的两次自我否定（为什么最终方案是这样）

这一节保留决策过程，因为**两次否定都是被证据推翻的**，读者需要知道我们排除了什么。

### 1.1 初版方案（已废弃）：自研薄模板引擎 + 重写 105 个端点

最初的路线 B 设想是"保留上游 `.htm` 视图 + 自研后端"，即自己写一个模板引擎渲染 `.htm`，
再把 105 个 `call()` 端点用别的语言实现一遍。

**放弃原因**：`luasrc/model/cbi/**` 下 15 个 CBI 表单页用的是 `luci.cbi` 框架——
`Value 233 / ListValue 109 / Flag 87 / Button 68 / DummyValue 59 / DynamicList 27 / Select 24`，
方法调用 `o:depends 483 / o:value 420 / s:option 234 / s:taboption 215`。
重写这些等于重写 LuCI 的 CBI 框架，**必然永久分叉，彻底违背"可同步上游"这一硬需求**。

### 1.2 第二版方案（已废弃）：vendor 现代 `luci-base`（ucode 版）

发现 LuCI 已经 Lua → ucode 迁移后，设想直接 vendor 现代 `luci-base`。

**放弃原因**（证据见 §2.3）：现代 `luci-base` 的 `ucode/` 里**没有 Lua 栈**，
Lua 侧只剩 `modules/luci-lua-runtime/luasrc/dispatcher.lua` 这一个**桥接文件**：

```lua
context = setmetatable({}, { ... })
build_url = _G.L.dispatcher.build_url      -- ← 调度树在 ucode 侧
menu_json = _G.L.dispatcher.menu_json
function process_lua_controller(path) ...  -- ← 由 ucode 调进来
function render_lua_template(path)  ...    -- ← 由 ucode 调进来
```

`_G.L` 必须由 ucode 预先注入。脱离 ucode 它**无法独立运行**。
而 ucode 版 `luci-base` 的依赖是
`+rpcd +rpcd-mod-file +rpcd-mod-luci +rpcd-mod-ucode +cgi-io +ucode +ucode-mod-{fs,log,uci,ubus,html} +liblucihttp-ucode`，
即必须跑 `ubusd` + `rpcd` 两个守护进程 —— 这正是用户明确否决的路线 A。

### 1.3 最终方案：vendor **纯 Lua 世代的 LuCI**（`openwrt-21.02`）+ 宿主兼容层

`openwrt-21.02` 分支的 `luci-base` 是**完整、独立、纯 Lua** 的实现，且自带两个宿主入口：

| 文件 | 作用 |
|---|---|
| `luasrc/sgi/cgi.lua` | **CGI 入口**：`luci.http.Request(luci.sys.getenv(), limitsource(io.stdin, CONTENT_LENGTH), ltn12.sink.file(io.stderr))`，然后把 `luci.dispatcher.httpdispatch` 当协程跑，响应写 stdout |
| `luasrc/sgi/uhttpd.lua` | uhttpd 私有协议入口（**不用**，它需要 `uhttpd` C 模块的 `recv`/`send`） |

**关键推论**：宿主的唯一契约就是「**提供一个 CGI 环境**」。
这既满足用户「不用 uhttpd」的要求（我们自己写宿主），又让上游入口代码零修改。

> 该分支自 2020 年起已冻结（OpenWrt 21.02 已是旧稳定版），因此：
> **它是一个稳定的、可 pin 的 vendor 依赖**；而真正需要每日同步的是 `luci-app-openclash` 本身。

### 2.2 上游入口形态：**必须 Lua 5.1**

* `luasrc/controller/openclash.lua:1` → `module("luci.controller.openclash", package.seeall)`
* `luasrc/openclash.lua:44` → `module "luci.openclash"`
* `luasrc/sgi/cgi.lua` → `module("luci.sgi.cgi", package.seeall)`

`module()` 与 `package.seeall` 在 Lua 5.2 中被移除。
⇒ 运行时必须是 **Lua 5.1**（Debian 包 `lua5.1`）。这不是可选项。

### 2.3 LuCI 的世代分裂（决定性证据）

| 分支 | `modules/luci-base/` 内容 | Lua 栈 |
|---|---|---|
| `master` | `htdocs/ po/ root/ src/ ucode/` | **无** |
| `openwrt-21.02` | `htdocs/ luasrc/ po/ root/ src/`（`luasrc/` 完整） | **完整** |

`master` 的 `luci-base/ucode/dispatcher.uc`：

```
L363: let files = glob('/usr/share/luci/menu.d/*.json', '/usr/lib/lua/luci/controller/*.lua', '/usr/lib/lua/luci/controller/*/*.lua');
L383: else if (load_luabridge(true)) data = runtime.call('luci.dispatcher', 'process_lua_controller', file);
L810: runtime.call('luci.dispatcher', 'render_lua_template', action.path);
L110: if (load_catalog(lang, '/usr/lib/lua/luci/i18n'))
```

⇒ 现代 LuCI 仍会**发现** `/usr/lib/lua/luci/controller/*.lua`，但执行要经过 ucode 的 Lua 桥
（`require('lua')`，来自 `ucode-mod-lua`）。所以 Lua 控制器/模板是「被 ucode 托管的」。

### 2.4 上游对 luci-base 的**运行时改写**

证据：`upstream/luci-app-openclash/root/etc/uci-defaults/luci-openclash:215-275`

```sh
# 1) 往 luci 的网络模型里注入 3 个函数
sed -i '/OpenClash Append/,/OpenClash Append End/d' /usr/lib/lua/luci/model/network.lua
cat >> /usr/lib/lua/luci/model/network.lua << EOF
-------------- OpenClash Append --------------
function get_all_wan_networks(self) ... end
function get_all_wan6_networks(self) ... end
function get_all_status_by_route(self, addr, mask) ...
    for _, object in ipairs(utl.ubus()) do ... end     -- ← 用到 ubus
end
-------------- OpenClash Append End --------------
EOF

# 2) 放大 HTTP 请求体上限（大配置文件编辑/上传需要）
sed -i '.../HTTP_MAX_CONTENT = 1024*10240/' /usr/lib/lua/luci/http.lua        # Lua 实现
sed -i '.../HTTP_MAX_CONTENT = 1024*10240/' /usr/share/ucode/luci/http.uc     # ucode 实现

# 3) 调大 uhttpd 的请求/连接/脚本超时（脚本超时对长任务很关键）
uci -q set uhttpd.main.max_requests=50
uci -q set uhttpd.main.max_connections=100
uci -q set uhttpd.main.script_timeout=3600
uci -q commit uhttpd
/etc/init.d/uhttpd restart
```

**三条推论**：
1. vendor 的 LuCI **必须落在上游硬编码的 OpenWrt 路径**（`/usr/lib/lua/luci/...`），否则这些 `sed` 全部落空。
   这条 sed 同时也是**行为依赖**：`HTTP_MAX_CONTENT` 不放大，上传大配置会 413/截断。
2. `uci set uhttpd.main.*` 要能成功写入 ⇒ 我们必须**提供 `/etc/config/uhttpd`**（见 §5.6）。
3. 注入的 ubus 调用**已被 `pcall` 包住**（`root/usr/share/openclash/openclash_get_network.lua:15`）：
   ```lua
   if pcall(function() local x = ntm:get_all_wan_networks(); ... end) then
   ```
   ⇒ ubus 缺失时上游走的是**自己的降级分支**，不需要我们伪造网络状态。

### 2.6 依赖与"能否零 C 编译"

| 组件 | 实现形态 | Debian 上的处理 |
|---|---|---|
| `lua` | C | `lua5.1` 包 ✅ |
| `luci-lib-base` | **纯 Lua**（`util/ltn12/http/debug.lua`） | vendor ✅ |
| `luci-base`（21.02） | **纯 Lua** | vendor ✅ |
| `luci-compat` | **纯 Lua**（`cbi.lua`、`cbi/datatypes.lua`、`model/network.lua`、`view/cbi/*.htm`） | vendor ✅ |
| `luci-lib-nixio` | C（`nixio.so`）**不依赖 libubox**（src 内零 ubus 引用，DEPENDS 仅 `liblua`/`libopenssl`） | 源码编译 ⚙️ |
| `luci-lib-ip` | C（`ip.so`）**依赖 `libnl-tiny`**（`#include <libnl-tiny/...>`，DEPENDS `+libnl-tiny`）；Debian 的 `libnl-3` **不能替代** | 源码编译 + libnl-tiny ⚙️ |
| ↳ `libnl-tiny` | C，独立仓库 `openwrt/libnl-tiny`（镜像 `git.openwrt.org/project/libnl-tiny.git`），**CMake 工程**，约 20 个 C 文件 | 源码编译 ⚙️ |
| `luci-lib-jsonc` | C（`jsonc.so`，绑定 `libjson-c`） | 源码编译 + `libjson-c-dev` ⚙️ |
| `liblucihttp` | C，独立仓库 **`jow-/lucihttp`**（MIT，CMake），提供 `lucihttp.so` | 源码编译 ⚙️ |
| `luci-lib-ipkg` | 纯 Lua | **刻意不装**（见下） |
| `rpcd` / `rpcd-mod-*` / `cgi-io` / `libubus-lua` | C + ubus 守护进程 | **替换**为进程内 session 模块（§5.5） |

**关于刻意不装 `luci-lib-ipkg`**：
上游 `controller/openclash.lua:131-135` 是
`if pcall(require, "luci.model.ipkg") then opkg = require "luci.model.ipkg" else opkg = nil end`。
若我们**装了**它，`opkg` 就非 nil，`coremodel()` 会走进 `opkg.info("libc")` 分支 ——
而 Debian 上没有 `opkg` 命令，该调用会失败（且可能抛错而不是返回 nil）。
若**不装**，`opkg = nil` 使上游走它自己写好的干净回退路径。
⇒ 这是一个**主动的、有依据的省略**，而不是遗漏。

**需编译的 C 模块共 6 个**（含 libnl-tiny 与 libuci 的 Lua 绑定），
全部是普通 `Makefile` / `CMakeLists.txt`，不需要 OpenWrt buildroot：

| 产物 | 源 | 编译要点 |
|---|---|---|
| `libnl-tiny.so` | `vendor/libnl-tiny` | CMake |
| `ip.so` → `/usr/lib/lua/luci/ip.so` | `vendor/luci/luci-lib-ip/src` | `-llua -lm -lnl-tiny`，头 `libnl-tiny/` |
| `nixio.so` → `/usr/lib/lua/nixio.so` | `vendor/luci/luci-lib-nixio/src` | `-DNO_TLS`（消掉 OpenSSL/axTLS 依赖）；`-llua -lm -ldl -lcrypt`；`NIXIO_SHADOW` 依赖 `getspnam` |
| `jsonc.so` → `/usr/lib/lua/luci/jsonc.so` | `vendor/luci/luci-lib-jsonc/src` | `-llua -lm -ljson-c`，头 `json-c/` |
| `lucihttp.so` → `/usr/lib/lua/lucihttp.so` | `vendor/lucihttp` | CMake（上游 CMake 已原生支持 Lua 5.1） |
| `po2lmo` | `vendor/luci/luci-base/src` | 随 luci-base vendor，用于生成 `.lmo` |

> 注意 `nixio.so` 与 `lucihttp.so` 装在 `/usr/lib/lua/` 下，而 `ip.so`/`jsonc.so`
> 装在 `/usr/lib/lua/luci/` 下 —— 这是 `require "luci.ip"` / `require "nixio"` 的
> Lua 模块解析路径决定的，不能弄错。

## 5. L2 宿主兼容层设计

### 5.1 路径契约（前端部分）

**硬规则：vendor 的 LuCI 必须落在上游硬编码的 OpenWrt 路径，不得改写。**

理由见 §2.4：上游 `uci-defaults` 与 `Makefile` 用绝对路径 `sed` 这些文件。
我们必须让 `docs/03-路径契约.md` §1 增补下表：

| 路径 | 提供者 | 被谁按绝对路径引用 |
|---|---|---|
| `/usr/lib/lua/luci/**` | luci-base + luci-compat + luci-lib-base + app | 上游 Makefile / uci-defaults / dispatcher 的 `package.path` |
| `/usr/lib/lua/luci/model/network.lua` | luci-compat | 上游追加 `OpenClash Append` 段 |
| `/usr/lib/lua/luci/http.lua` | luci-lib-base | 上游改 `HTTP_MAX_CONTENT` |
| `/usr/lib/lua/luci/i18n/*.lmo` | 上游 po/ | dispatcher 的 `load_catalog` |
| `/usr/lib/lua/nixio.so` | 编译 | `require "nixio"` |
| `/usr/share/ucode/luci/http.uc` | —（**不存在**） | 上游那条 `sed` 会静默落空，可接受 |
| `/www/luci-static/resources/openclash/**` | app `root/` | 视图里的静态引用 |
| `/var/run/luci-sessions/` | 我们的 session 模块 | dispatcher 的会话存储 |
| `/tmp/luci-indexcache*`、`/tmp/luci-modulecache` | dispatcher 自建 | 上游 `uci-defaults` 会 `rm -rf` 它们 |

### 5.2 Lua 5.1 运行时

* 依赖 `lua5.1`；`package.path` 需含 `/usr/lib/lua/?.lua`、`/usr/lib/lua/?/init.lua`、`/usr/lib/lua/luci/?.lua`。
* `lua5.1` 的 `package.cpath` 需含 `/usr/lib/lua/?.so`。
* 入口脚本 `/usr/lib/cgi-bin/luci`：
  ```lua
  #!/usr/bin/lua5.1
  require("luci.sgi.cgi").run()
  ```
  （上游 `luci-base` 的 `htdocs/cgi-bin/luci` 已是同形态，优先直接复用其文件）

#### 5.2.1 ⚠️ `/usr/bin/lua` 必须是 Lua 5.1（硬要求）

上游 `root/usr/share/openclash/` 下有 **8 个被直接执行的脚本**，shebang 全部是
`#!/usr/bin/lua`：

```
openclash_debug_dns.lua        openclash_oix_checkin.lua
openclash_debug_getcon.lua     openclash_streaming_unlock.lua
openclash_get_network.lua      openclash_sub_parser.lua
                               openclash_urlencode.lua
                               openclash_version.lua
```

而它们是被上游**按路径调用**的，例如
`luasrc/model/cbi/openclash/settings.lua:421`：
```lua
SYS.exec("/usr/share/openclash/openclash_get_network.lua 'gateway6'")
```
⇒ 由内核按 shebang 解析解释器，**我们无法干预**（改 shebang 等于改上游代码，违反 L1 红线）。

风险：若目标机器上已有 `/usr/bin/lua` 指向 **Lua 5.3/5.4**（常见于同时装了其他 Lua 软件包的服务器），
这 8 个脚本会以「语法/标准库不兼容」的方式崩溃，而报错信息与 OpenClash 毫无关联，极难定位。

应对（**打包期改写，不是注册 alternatives**）：
1. `Depends: lua5.1`（提供 `/usr/bin/lua5.1`）。
2. ~~`update-alternatives --install /usr/bin/lua lua-interpreter /usr/bin/lua5.1 100`~~
   —— **该方案已废弃**，理由见下方更正块。
3. 打包期用 `runtime/upstream/pin-lua-interpreter.sh` 把上游 11 处「依赖系统
   `lua`」的写法**就地改写成绝对路径 `/usr/bin/lua5.1`**（8 个 shebang +
   3 处显式 `lua <路径>` 调用），`upstream/` 源树保持逐字节原样。
4. 校验方式随之变成「**宽判据必须归零**」：staging 树里命令位置上不得再有任何
   裸 `lua`。详见 `docs/03-路径契约.md` §1.4 与 `docs/04-ubus依赖图谱.md` §2.3。

> ⚠️ **已更正一次（本段原先写的 alternatives 方案是错的）。**
> **为什么不用 `update-alternatives`**：
> 1) 它会改动**全系统**的 `lua` 默认解释器，对用户不礼貌；
> 2) 更关键：该组若已被置为 **manual** 模式，新注册的高优先级候选**不会**自动
>    生效 —— 等于没有任何保证。绝对路径没有这个盲区，也不碰系统既有的
>    alternatives 组，卸载时无需回滚。
>
> **为什么"校验 `lua -v`"也不够**：校验发生在**安装期**，而崩溃发生在**运行期**
> —— 上游有 8 个 `#!/usr/bin/lua5.1` 脚本会被 cron 里的 `openclash_watchdog`
> 在任意时刻拉起。中间只要有人再装一个 lua5.4 并把 alternatives 切过去，就是
> 静默失效。所以必须在**打包期**把依赖改成不依赖 `PATH`/alternatives 的绝对路径。

### 5.3 `nixio`：编译上游源码，**不写替代品**

* `nixio` 是上游 C 代码且**不依赖 libubox**，Debian 上可直接编。
* 必须保留的语义（有实际调用点，不能简化）：
  * `nixio.fs.readfile(path, blocksize)` 返回的是 **chunk 函数**，要能配合 `luci.ltn12.pump.all` 做流式读取（7 处）
  * `nixio.fs.stat()` 返回结构化表（`size`/`mtime`/`type`…），`luci.openclash.stat` 依赖它
  * `nixio.fs.dir()` 返回**迭代器**（`luci.openclash.dir`）
  * `nixio.fs.glob`、`nixio.const.buffersize`（4 处）
  * `nixio.util.consume`（2 处）
* 风险：`nixio` 的 `src/Makefile` 面向 OpenWrt staging，需移植为「`lua5.1` 头文件 + gcc」的形式。
  这是 P1 的第一个任务，**先做它**，因为它决定后面所有 Lua 代码能否跑起来。

### 5.4 `uci`：复用真实 libuci 的 Lua 绑定

* 复用 `runtime/uci/build-uci.sh`（libubox + uci + Lua 绑定）。
* 额外必须实现的行为：**`ucitrack` 触发**。
  上游自带 `/usr/share/ucitrack/luci-app-openclash.json`：
  ```json
  { "config": "openclash", "init": "openclash" }
  ```
  含义是「`openclash` 配置被 commit 后，调用 `/etc/init.d/openclash`」。
  我们的 `uci` 绑定或 `luci.model.uci` 包装层必须读取 `/usr/share/ucitrack/*.json` 并触发，
  **否则 Web UI 改配置后服务不会自动 reload**——这是"看起来能用但行为不对"的典型陷阱。
* `lanip()` 已核实**原生可移植**（`luasrc/openclash.lua:299-314`）：
  四条回退路径里三条是通用 Linux 命令（`ip address show <if>` / `ip addr show | grep global | grep brd`），
  只有 `uci -q get network.lan.ipaddr` 是 OpenWrt 专有且失败无害（`2>/dev/null`）。
  ⇒ 旁路网关场景**建议在 UI 里显式设置 `lan_interface_name`**，走确定性分支。

### 5.5 `ubus` → **进程内 session 模块**（本设计的关键自研件）

不实现 ubus 总线，只实现 `luci.util.ubus()` 所使用的调用形态：

```
util.ubus("session", "login",   { username, password, timeout })
util.ubus("session", "get",     { ubus_rpc_session })
util.ubus("session", "access",  { ubus_rpc_session, scope, object, function })
util.ubus("session", "set",     { ubus_rpc_session, values })
util.ubus("session", "destroy", { ubus_rpc_session })
util.ubus()          → 返回空表（让注入的 get_all_status_by_route 自然空转）
util.ubus(其它对象)   → 返回 nil / false（上游 pcall 保护，降级）
```

设计要点：
1. **会话存储**：`/var/run/luci-sessions/<sid>`，`sid` 用 `md5(rand+time+user)`；权限 `0600`；含 `username`/`expiry`/`values`。
   目录与 LuCI 的 `luci.config.sauth.sessionpath` 对齐。
2. **口令校验**：读 `/etc/shadow` 的 `$6$`/`$y$` 哈希，用 Lua 的 `crypt`（`lua-crypt` / `posix.crypt`）比对；
   若不引入 `posix`，退化为调用 `python3 -c 'import crypt'` 或 `openssl passwd`。**需在 P1 敲定**（见 §10 未决项 U3）。
3. **ACL**：读 `/usr/share/rpcd/acl.d/*.json`。
   上游自带的 `luci-app-openclash.json` 正好授权 `uci: ["openclash"]` 的读写 ——
   **沿用上游声明，不另立一套**（这是「喂上游的探测」范式在鉴权上的应用）。
4. **`scope` 语义**：`session.access` 返回 `{ access = true/false, ... }`，字段名必须与 rpcd 一致，否则 dispatcher 的鉴权判断会静默失败。
5. **降级开关**：提供 `openclash-rt` 自己的配置项允许「无鉴权直通」（本机代理场景下方便），但**默认必须开启鉴权**，
   因为它会监听 TCP，暴露 shell 执行能力（105 个端点能跑任意脚本）。

### 5.6 HTTP 宿主（自研，唯一契约是 CGI）

**契约**：宿主对每个动态请求提供标准 CGI 环境并运行 `/usr/lib/cgi-bin/luci`，
把 stdout 解析成 HTTP 响应。这样上游 `luci.sgi.cgi.run()` 零修改即可工作。

宿主职责清单：

| # | 职责 | 说明 |
|---|---|---|
| H1 | 静态文件服务 | 根目录 `/www`；`/luci-static/**` 等 |
| H2 | 动态路由 | `/cgi-bin/luci[/<PATH_INFO>]`；`PATH_INFO` 必须正确切分（LuCI 靠它做菜单路由） |
| H3 | CGI 环境变量 | `REQUEST_METHOD/REQUEST_URI/PATH_INFO/SCRIPT_NAME/QUERY_STRING/CONTENT_TYPE/CONTENT_LENGTH/SERVER_*/REMOTE_*/DOCUMENT_ROOT/HTTP_*` |
| H4 | 请求体转发 | 按 `CONTENT_LENGTH` 从 stdin 喂给子进程；支持 `PUT/POST`、`multipart/form-data` 上传 |
| H5 | 响应解析 | `Status:` 行 → HTTP 状态码；头 → 响应头；支持 `Set-Cookie` 多值 |
| H6 | **`HTTP_MAX_CONTENT`** | 从 `/etc/config/uhttpd` 读取（见下），默认跟随上游改写值 `1024*10240`，否则大配置上传会截断 |
| H7 | 超时 | `script_timeout`（默认 3600，上游要求）；必须**大于**上游最长任务（内核下载/规则更新） |
| H8 | 并发 | `max_requests=50` / `max_connections=100`（上游要求值） |
| H9 | 子进程回收 | 客户端断开时必须终止子进程，避免 105 个端点里的长任务泄漏 |
| H10 | 监听 | 默认绑定 `0.0.0.0:80`？**不**——默认绑 `127.0.0.1:9090`，由用户显式开启外部监听（安全默认） |

**为什么提供 `/etc/config/uhttpd`**：
上游 `uci-defaults` 会执行 `uci -q set uhttpd.main.{max_requests,max_connections,script_timeout}` +
`uci -q commit uhttpd` + `/etc/init.d/uhttpd restart`。

* 若该配置文件不存在，真实 uci 的 `set` 会报错、`commit` 落空 → **上游的意图丢失且无提示**。
* 我们提供一份带 `config uhttpd 'main'` 的 `/etc/config/uhttpd`（**具名段**，理由同后端的 `dhcp.main`），
  上游的写入就会真的落进去，宿主再从中读取。
  ⇒ 语义可见、可排障、可被用户覆盖，且完全沿用上游的写入代码。

另需提供 `/etc/init.d/uhttpd`（rc.common 形态），把 `restart` 映射到宿主的 systemd 单元 restart，
使上游那条 `/etc/init.d/uhttpd restart` 真正生效。

### 5.7 i18n

* 用 luci-base 自带的 `po2lmo`（C，`src/po2lmo.c`）把上游 `po/zh-cn/*.po` 编成 `.lmo`。

`runtime/sys/openwrt-release.sh`：把 `dpkg --print-architecture` 翻译成 OpenWrt 的 `DISTRIB_ARCH`，
使上游 `uci-defaults` 的 `case` 算出正确的 `CORE_ARCH`，进而 `openclash.config.core_version` 正确、内核下载链接正确。

* 值用**单引号**（`controller/openclash.lua:184` 用 `match("DISTRIB_ARCH='([^']+)'")` 取值）

### 5.9 上游对 luci-base 的改写如何落地

**不在 vendor 阶段打补丁**（那会让 vendor 树与上游不一致，破坏可同步性）。
而是**在安装期复刻上游自己的行为**：把 `root/etc/uci-defaults/luci-openclash` 原样执行一次
（它就是上游为此写的脚本）。

这就要求我们的环境中：
* `/usr/lib/lua/luci/model/network.lua` 存在（vendor 提供）→ 追加成功
* `/usr/lib/lua/luci/http.lua` 存在（vendor 提供）→ `HTTP_MAX_CONTENT` 放大成功
* `/usr/share/ucode/luci/http.uc` 不存在 → 那条 `sed` 静默落空（可接受，因为我们不用 ucode）
* `uci set uhttpd.main.*` 成功（我们用 `/etc/config/uhttpd` 兜住）
* `/etc/init.d/uhttpd restart` 成功（我们用 compat initscript 兜住）

**另有隐患**：`uci-defaults` 的 `Restore` 段用 `mv` 覆盖 `/etc/config/openclash`，
并且会 `rm -rf` 一批路径。它是幂等的但**有破坏性**，所以：
* 只在**首次安装**执行（用 `/etc/openclash/.uci-defaults-done` 标记）
* 在 `prerm` 里**不**执行

## 6. 前端 ↔ 后端的连接点

前端 105 个端点全部落在 `luci.dispatcher` 的 `call()` 上，它们做的是：

```
call("action_xxx")
   → luci.sys.call("/usr/share/openclash/openclash_xxx.sh ...")   -- 82 次
   → luci.sys.exec(...)                                            -- 74 次
   → luci.http.write_json{...}                                     -- 115 次
```

⇒ **前端与后端之间没有 RPC，只有 shell 调用与 JSON**。
所以后端兼容层（`docs/03`）一旦跑通，前端就自动跑通——两个阶段**天然解耦**，
这是一个非常有利的工程性质。

需要前端注意的唯一耦合点：`luci.sys.call` 依赖 `LUCI_*` 环境与 `PATH`，
而 105 个端点会以 **Web 进程的身份**执行 `/etc/init.d/openclash ...`。
⇒ 宿主必须以 **root** 运行（上游在 OpenWrt 上也是 root），
并在 `docs/03` 的路径契约里登记「前端执行脚本时可用 `uci`/`fw4`/`iptables-nft`」这一前提。
