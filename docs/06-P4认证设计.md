# 06 · P4 认证设计：进程内 ubus session 模块

> 测绘结论 + 实现蓝图。测绘基于 vendor/rpcd/session.c 与
> vendor/luci/luci-base/luasrc/dispatcher.lua，全部在 Debian 真机（172.20.0.101）核实。

## 0. 一句话结论

不实现 ubus 总线，只实现 `luci.util.ubus("session", ...)` 用到的 4 个方法
（login/get/access/set），通过 `package.loaded["ubus"]` 预注入一个纯 Lua 假 ubus 模块，
让上游 dispatcher 无感知地走本地 session 逻辑。session 状态持久化到磁盘
（`/tmp/luci-sessions/<sid>`），因为每个 HTTP 请求都 fork 独立 CGI 进程，内存态无法跨请求存活。

## 1. 测绘结论（接口契约，来自 session.c + dispatcher.lua）

### 1.1 dispatcher 用到的 4 个方法

| 方法 | 入参 | 返回 | dispatcher 用法 |
|---|---|---|---|
| `login` | username, password, timeout | `{ubus_rpc_session, timeout, expires, acls, data}` | session_setup (549) |
| `set` | ubus_rpc_session, values{token=...} | 空 | session_setup (562) |
| `get` | ubus_rpc_session | `{values{username,token,...}}` | session_retrieve (533) |
| `access` | ubus_rpc_session | `{scope:{obj:[func]}}` 全 dump | session_retrieve (534) + admin/index (191) |

### 1.2 session 有效性判定（dispatcher.lua:532 session_retrieve）

```lua
sdat = util.ubus("session","get",{ubus_rpc_session=sid})
sacl = util.ubus("session","access",{ubus_rpc_session=sid})
-- 有效条件：sdat.values 是 table 且 sdat.values.token 是 string
-- 权限：sacl["access-group"] 里的 group 列表
```

### 1.3 口令校验（session.c:820 rpc_login_test_password + rpc_login_test_login）

- 登录源 = UCI 包 `rpcd` 里 `config login` 段（username + password 选项）。
- 三种口令形态：
  1. 空 hash → 通过（无密码）
  2. `$p$<user>` → 引用系统 shadow/passwd 的 `<user>`
  3. 普通 crypt 哈希 → `crypt(password, hash)` 比对
- `nixio.crypt` 已可用（真机实测 `nixio.crypt("password", "$6$salt$...")` 返回 SHA-512 crypt，
  nm 显示链 `crypt@XCRYPT_2.0`）。**U3 未决项就此敲定：用 nixio.crypt，零额外依赖。**

### 1.4 ACL 读取（session.c:1042 rpc_login_setup_acls）

- glob `/usr/share/rpcd/acl.d/*.json`，逐个 parse。
- json 结构：`{ "<group>": { "read"/"write": { "<scope>": [obj] 或 {obj:[func]} } } }`
- login 段的 `read`/`write` 选项 = 该用户所属的 group 列表（空格分隔）。
- 每个 json 里 read/write 权限属于该 group 时，把 `<scope>/<obj>/<func>` grant 进 session，
  同时把 group 本身写入 `access-group` 元 scope。

### 1.5 关键配置（vendor/luci/luci-base/root/etc/config/luci）

```
config internal sauth
	option sessionpath "/tmp/luci-sessions"
	option sessiontime 3600
```

## 2. 已发现的 2 个前置缺口（P4 必须一并修）

1. **`luci-app-openclash.json` 未落位**：上游
   `upstream/luci-app-openclash/root/usr/share/rpcd/acl.d/luci-app-openclash.json`
   授权 `uci: ["openclash"]` 读写，但 `install-vendor-luci.sh` 只装 luci-base/luci-compat
   的 acl.d，漏了这个。缺了它，登录成功也会因 `access-group` 缺 `luci-app-openclash`
   而被 dispatcher 拒在 `/admin/services/openclash/*` 门外。
   → 修：install-vendor-luci.sh 或 build-deb 补装上游 acl.d。

2. **`/etc/config/rpcd` 无 login 段**：真机该文件为空，登录无从校验。
   → 修：提供默认 `/etc/config/rpcd`，login 段引用系统 root（`$p$root`），
   与 Debian root 密码对齐（标准 LuCI 行为：root + root 密码）。

## 3. 实现方案

### 3.1 假 ubus 模块注入（不碰上游）

Lua 5.1 `require` 先查 `package.loaded`。在 CGI 子进程里、`luci.util` require "ubus" 之前，
把 `package.loaded["ubus"] = fake_ubus` 即可完全接管。

注入时机：`/www/cgi-bin/luci` 第一个 require 是 `luci.cacheloader`。利用 Lua 5.1 的
`LUA_INIT` 环境变量（支持 `@file` 引导），在 fork CGI 子进程前设置
`LUA_INIT=@/usr/lib/openclash-rt/luci-session-bootstrap.lua`，由 bootstrap 做 preload 注入。

### 3.2 fake ubus 模块接口

```lua
-- require("ubus") 返回的模块
M.connect = function(path, timeout) return connection end
-- connection 对象
connection:call(object, method, data)
connection:objects()      -- 返回 {} 或空表
connection:signatures(o)  -- 返回 {}
```

`call("session", method, data)` 分发到本地 session 实现；
`call(其它, ...)` 返回 nil（上游 pcall 保护）。

### 3.3 本地 session 实现（runtime/sys/luci-session.lua）

- **存储**：`/tmp/luci-sessions/<sid>`，JSON 格式 `{username, expires, token, values}`，
  权限 0600。sid = `md5(rand + time + username)` 前 32 hex（对齐 rpcd RPC_SID_LEN=32）。
- **login**：读 UCI `rpcd` 的 login 段 → 校验口令（nixio.crypt）→ 建 session →
  返回 `{ubus_rpc_session, timeout, expires, acls, data}`。
- **get**：读磁盘 session 文件 → 返回 `{values={username,token,...}}`。
- **access**：读 session 文件 + glob acl.d/*.json + login 段 read/write group →
  返回 `{<scope>:{<obj>:[<func>]}, access-group:{<group>:[read/write]}}`。
- **set**：更新 session 文件里的 values（token 等）。
- **destroy**：删 session 文件。

### 3.4 UCI 读写

用 `/sbin/uci`（已由 build-uci 编译 + postinst 落位）读 `rpcd` 包的 login 段。
用 `nixio.fs` 读 `/etc/config/rpcd` 或直接 `uci get`。

## 4. 验收口径（P4，docs/02 §9.6）

1. 未登录访问 `/admin/services/openclash/*` → 跳登录页。
2. 错误口令被拒（login 返回 PERMISSION_DENIED）。
3. 正确口令登录 → set-cookie sysauth → 能进 `/admin/services/openclash/client`。
4. 会话超时（sessiontime 3600s）后失效。
5. 机器上无 ubusd/rpcd/uhttpd 进程（§9.8）。

## 5. 重大修正（2026-10-02 端到端验证发现）

**P4 不只是 session，还依赖 uci 对象。**

端到端测试 `conf.main` 为 nil，追到 `luci.model.uci.get_all` 内部用
`util.ubus("uci", "get", args)` 走 ubus 总线（不是直接调 uci C 绑定）。
所以假 ubus 模块必须同时接 **uci** 对象，否则连 `luci.config`（读 /etc/config/luci）
都过不去，前端一行都渲染不了。

**uci 对象的完整方法面**（来自 luci.model.uci 的 call() 调用点）：
- 读：`get`
- 写：`add`、`set`、`delete`、`order`
- 事务：`changes`、`commit`、`apply`、`confirm`、`revert`、`rollback`

**最优实现 = 委托给已编译的 uci C 绑定**（build-uci.sh 产物，真机实测
`require "uci"` + `cursor():get_all()` 可用），不重新实现事务语义。
rpcd 的 uci 插件底层也是 libuci，两者等价。

```lua
-- 假 ubus 的 uci 对象实现
local uci = require "uci"
local cur = uci.cursor()
-- call("uci", "get", {config=, section=}) → { values = cur:get_all(config, section) }
-- call("uci", "set", {config=, section=, values=}) → 逐项 cur:set + commit
-- ...
```
