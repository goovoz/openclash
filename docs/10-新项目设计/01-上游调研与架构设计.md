# 10 · 新项目设计：Linux 无桌面 mihomo 客户端

> 目标：全新自研 Linux 服务器（无桌面）mihomo 客户端
> - 同时支持**本机代理**与**旁路由**
> - 兼容机场订阅（shadowsocks/R、vmess、trojan、snell 等）
> - 灵活规则配置与策略代理
>
> 日期：2026-10-03
> 状态：**调研完成 + 方向已定**，待评审
> 技术选型：**Rust** / 自研 Web UI（zashboard 仅用于节点选择）
> 验证环境：复用现有 Debian 虚拟机 172.20.0.101做旁路由，OpenWrt .2 做客户端

## 1. 上游调研结论（实测，非文档推断）

调研方式：抓官方 wiki（`wiki.metacubex.one`，MkDocs Material 静态页，
curl + 剥标签，脚本 `scripts/_probe/html2text.py`），
并用**真机上 OpenClash 带的 mihomo 二进制**做能力探测
（`scripts/_probe/probe-mihomo-caps.py`，用 `mihomo -t` 逐项校验）。

### 1.1 内核形态

```
$ /etc/openclash/core/clash_meta -v
Mihomo Meta alpha-smart-g2e80ed7 linux amd64 with go1.26.5
Use tags: with_gvisor
```

命令行能力（决定客户端能做什么）：

```
  -t                    测试配置后退出     ← CI/原子切换必备
  -f / -d               指定配置/目录
  -config               直接给 base64 配置串
  -ext-ctl              RESTful API 地址
  -ext-ctl-unix         API 走 unix socket ← 免端口暴露
  -ext-ctl-pipe         API 走管道        ← 同上
  -ext-ctl-tls          API 走 TLS
  -ext-ui               Web UI 目录
  -secret               覆盖 API 密钥
  -age-secret-key       age 加密配置解密
  -post-up / -post-down 启停钩子
  -m                    geodata 模式
```

**结论 1：内核已内置配置校验与安全 API 通道，客户端不需要自己实现
协议解析、配置校验、API 安全。三项都能委托。**

### 1.2 协议支持（`-t` 实测）

用户要求的全部支持：

| 协议 | type | 实测 |
|------|------|------|
| Shadowsocks | `ss` | ✅ |
| Shadowsocks-R | `ssr` | ✅ |
| VMess（含 ws） | `vmess` | ✅ |
| Trojan | `trojan` | ✅ |
| Snell | `snell` | ✅ |

额外确认：`hysteria2` / `tuic` / `wireguard` / `anytls` / `http` /
`socks5` / `shadowsocks-2022` / `vless+reality`。

> 探针踩坑：`-t` 失败只说 "test failed"，**分不清是协议不支持还是
> 引用了不存在的代理组名**。第一版探针漏填`proxies[].name` 到
> `proxy-groups.proxies`，导致一半协议误判为 no。

### 1.3 透明代理三模式

| 模式 | 配置项 | 覆盖| 机制 |
|------|--------|------|------|
| redir | `redir-port` | TCP | `REDIRECT` + `SO_ORIGINAL_DST` |
| tproxy | `tproxy-port` | TCP+UDP | `TPROXY` + `IP_TRANSPARENT`，内核 ≥2.6.28 |
| TUN | `tun:` | TCP+UDP+ICMP | 内核态虚拟网卡 |

` tun` 完整字段（官方 wiki `config/inbound/tun`）：

```yaml
tun:
  enable: true
  stack: mixed              # system|gvisor|mixed|mips，默认 gvisor
  device: Mihomo
  auto-route: true
  auto-redirect: true          # 仅 Linux：mihomo 自己写 iptables/nftables
  auto-detect-interface: true
  dns-hijack: ['any:53', 'tcp://any:53']
  strict-route: true           # Linux 上防地址泄漏
  mtu: 9000
  gso: true                    # 仅 Linux
  inet6-address: [fdfe:dcba:9876::1/126]
  udp-timeout: 300
  iproute2-table-index: 2022   # auto-route 生成的路由表索引
  iproute2-rule-index: 9000
  endpoint-independent-nat: false
  include/exclude-interface: [eth0]
  include/exclude-uid / -uid-range
  include/exclude-mac-address
  route-address / route-exclude-address
  route-address-set / route-exclude-address-set   # 需 nftables + auto-redirect
```

四个对我们特别重要的能力：

1. **`auto-redirect`**（Linux 专有）—— **不用手写 nftables**，mihomo 自己配转发。
   OpenClash 最大的复杂度来源就是自己维护 `openclash_wan_input` 那套规则。
2. **`route-address-set`** —— 规则集直接注入 nftables，**这类流量根本不进内核**，
   旁路由性能的关键。
3. **`strict-route`** —— Linux 上防 DNS 泄漏。
4. **`include-uid` / `exclude-uid`** —— 按 UID 绕过，**解环路的核心手段**。

### 1.5 DNS（官方 wiki `config/dns`）

```yaml
dns:
  enable: true
  listen: 0.0.0.0:1053
  enhanced-mode: fake-ip       # fake-ip | redir-host
  fake-ip-range: 198.18.0.1/16
  fake-ip-filter-mode: blacklist
  fake-ip-filter: ['*.lan']
  cache-algorithm: lru          # lru | arc
  prefer-h3: false
  respect-rules: false
  default-nameserver: [223.5.5.5]
  nameserver: [...]
  nameserver-policy:
    '+.arpa': '10.0.0.1'
    'rule-set:cn': [...]
  fallback: [...]
  fallback-filter: {geoip: true, geoip-code: CN, geosite: [gfw]}
  proxy-server-nameserver: [...]      # ★ 解析节点域名，防死锁
  direct-nameserver: [system]
```

**★ 旁路由第一坑**（我们真机踩过）：`proxy-server-nameserver` 必须指向
**可直连**的 DNS。OpenClash 改成 DoH后节点域名解析失败
（`doh.pub` 8 秒超时），叠加 fake-ip 劫持 53 端口 → 所有节点不可用。

### 1.6 规则（官方 wiki `config/rules`）

40+ 种规则类型，**从上到下首次命中即生效**：

```
DOMAIN  DOMAIN-SUFFIX  DOMAIN-KEYWORD  DOMAIN-WILDCARD  DOMAIN-REGEX
GEOSITE  IP-CIDR  IP-CIDR6  IP-SUFFIX  IP-ASN  GEOIP
SRC-IP-CIDR  SRC-IP-SUFFIX  SRC-IP-ASN  SRC-GEOIP
DST-PORT  SRC-PORT  IN-PORT  IN-TYPE  IN-USER  IN-NAME  REMATCH-NAME
PROCESS-NAME{,-REGEX,-WILDCARD}  PROCESS-PATH{,-REGEX,-WILDCARD}
UID  NETWORK  DSCP  RULE-SET
AND / OR / NOT / SUB-RULE / MATCH
```

附加参数：
- `no-resolve` —— 仅对目标 IP 类规则有效。**不加会触发 DNS 解析**
  （既慢，又可能因解析失败漏命中）
- `src` —— 目标 IP 匹配转为来源 IP 匹配

逻辑规则（官方示例）：

```yaml
- AND,((DOMAIN,baidu.com),(NETWORK,UDP)),DIRECT
- OR,((NETWORK,UDP),(DOMAIN,baidu.com)),REJECT
- SUB-RULE,(NETWORK,tcp),sub-rule
```

## 2. OpenClash 架构分析（该学什么、该避开什么）

### 2.1 它的规模

```
73 个 controller 端点
30 个 view 页面
核心脚本（shell）：
  yml_proxys_get.sh     60 KB
  yml_proxys_set.sh     49 KB
  yml_change.sh         35 KB
  openclash_watchdog.sh 23 KB
  yml_rules_change.sh   21 KB
  openclash.sh          16 KB
  openclash_core.sh      9 KB
  yml_groups_set.sh      8 KB
```

### 2.2 该避开的（它的技术债）

1. **UCI 抽象层**。OpenClash 把所有配置塞进 UCI 的 `section`/`option`，
   于是出现「一段option 存不进去」「cbid 前缀要跟段名一致」「
   `pageaction=false` 导致整页不保存」这类问题 ——
   **我们上一轮实测的 Add 按钮与内核启动失败，根因就是 cbid 前缀
   与 uci 段名不一致。**

2. **多脚本协同 + 隐式契约**。`openclash.sh` 调`yml_change.sh` 再调
   `yml_groups_set.sh`，参数靠位置传，出错时没有事务性。

3. **配置是"生成"而非"数据"**。订阅、用户覆写、规则全靠脚本反复改同一个
   yaml 文件。OpenClash 后来靠 `ruby`+`YAML` 库做结构化读写（见
   `yml_proxys_get.sh` 里的 `ruby -ryaml -e`），但仍依赖 OpenWrt 的 ruby 包。

### 2.3 该借鉴的

1. **`auto-redirect` 思路**：让 mihomo 自己管防火墙规则，而不是自己写
   nftables。OpenClash 维护 `openclash_wan_input` 那套规则是主要复杂度来源。
2. **watchdog 的职责划分**：进程守护 + 节点可用性检查 + 防火墙自愈 +
   证书/IP 更新，而且是**独立进程**而非塞进主脚本。
3. **订阅的多维元数据**：`address` / `ua` / `sub_convert` / `emoji` /
   `udp` / `skip_cert_verify` / `sort` / `node_type` / `rule_provider`
   （见 `config-subscribe.lua`）—— 这些字段设计得不错，值得直接沿用。
4. **启动前分步校验**（`openclash_start.log` 里的 Step 1~6）：
   取配置 → 查组件 → 改配置 → 起内核 → 起守护 → 查状态 + 设防火墙。
   这个**分阶段可观测**的流程值得保留。

### 2.4 功能面归类（不该照抄 73 个端点）

OpenClash 的 73 端点按域归类后，是我们要做的功能清单：

| 功能域 | OpenClash 端点（示例） | 本项目是否要 |
|--------|----------------------|------------|
| **运行控制** | `switch_mode` `switch_run_mode` `switch_log` `flush_dns_cache` `close_all_connection` `stop`/`start` | ✅ 核心 |
| **节点选择** | `proxy_info` `conn_status` `dashboard_type` `switch_dashboard` | ✅ 核心 |
| **订阅管理** | `add_subscription` `get_subscribe_data` `update` `switch_config` `config_file_*` | ✅ 核心 |
| **配置编辑** | `oc_settings` `switch_oc_setting` `overwrite_file_*` `upload_config` | ✅ 核心 |
| **内核管理** | `check_core` `one_key_update` `save_corever_branch` `remove_all_core` `add_age_config` | ✅ 核心 |
| **规则/日志** | `switch_rule_mode` `get_run_mode` `startlog` `del_log` `gen_debug_logs` | ✅ 核心 |
| **诊断** | `myip_check` `website_check` `addr_info` `diag_connection` `diag_dns` `announcement` `last_version` | ⭕ 精选（4~5 个） |
| **外链业务** | `oix_login` `oixcloud` `subconverter_version` `generate_age_key` `server_url` | ❌ 不做（与代理无关） |
| **地理数据库** | `geox-url` `geo-auto-update` | ✅ 内核自带，不用我们管 |

**结论：本项目的功能面约为 OpenClash 的 60%，但代码量可以小一个量级**
（无UCI、无 LuCI、无 OpenWrt 依赖）。

## 3. 架构设计

### 3.1 组件划分

```
┌───────────────────────────────────────────────────────┐
│  控制面（自研，Rust）│
│  ┌──────────┐┌──────────┐  ┌──────────────┐            │
│  │ Web UI   ││ CLI      │  │ 客户端 API   │           │
│  │ (静态)   ││ clap     │  │ (REST,单端口) │           │
│  └────┬─────┘└────┬─────┘  └──────┬───────┘           │
│       └───────────┼───────────────┘                    │
└───────────────────┼────────────────────────────────────┘
                    │ unix socket（首选）/ 127.0.0.1 + token
            ┌───────┴────────┐
┌───────────┴─────────────────────────┐
│            mihomo 内核                │
│  显式入站 mixed/socks/http（本机代理） │
│  透明入站 tun / redir / tproxy（旁路由）│
│  RESTful API                          │
└─────────────────────────────────────────┘
```

**核心决策：客户端不做任何协议解析。**
代理连接全部由 mihomo 的显式入站承担；客户端只负责：
生成正确 YAML + 管 systemd + 操作内核 API + 提供界面。

### 3.2 两种模式是连续谱，不是二选一

用户要求「同时支持本机代理 + 旁路由」。mihomo 本身就能同时开：

| 维度 | 本机代理 | 旁路由 |
|------|---------|--------|
| 显式入站 | `mixed-port` + `bind-address: 127.0.0.1` | `mixed-port` + `bind-address: 0.0.0.0` |
| 透明入站 | 关 | `tun.enable: true`（推荐）或 redir/tproxy |
| 路由表 | 不动 | `tun.auto-route` 自动建 |
| DNS 劫持 | 不做 | `tun.dns-hijack: [any:53]` |
| 防火墙 | 不碰 | `auto-redirect` 让 mihomo 自己写 |
| `interface-name` | 不设| 设上游 WAN 网卡 |

UI 上做成「**旁路由开关**」+「**出口网卡选择**」两个控件即可。

### 3.3 旁路由的环路问题（核心风险，必须处理）

流量从 lan 网卡进来 → 代理 → 又从 lan 网卡出去 → 再进来。
三种防法（**可组合，缺一不可**）：

1. **`interface-name`** —— 指定**出口**网卡。流量从别的网卡进来时明确走 WAN。
2. **专用用户 + `exclude-uid`** —— systemd 让mihomo 以专用 UID 运行，
   `tun.exclude-uid` 让它自己的连接绕过。
   OpenClash 正是用 `uid=nobody`；mihomo discussions #1325 里
   **漏掉这一步直接导致 loopback error**。
3. **`exclude-interface`** —— 明确排除不该进 TUN 的网卡。

> 这是我们要重点验证的部分（见 §5）。

### 3.4 配置生成与原子切换

```
用户配置（UI/CLI/配置文件）
        ↓
   Rust 渲染器（serde_yaml，操作数据结构）
        ↓
  完整 mihomo YAML  ← 内置模板 + 订阅节点 + 规则集
        ↓
  mihomo -t 校验    ← ★ 必须过！失败则拒绝切换并报错
        ↓
  reload（PATCH /configs）或 systemctl reload
```

**绝不像 OpenClash 那样用 sed/awk 改 yaml。**
我们在真机被 `yml_change.sh` 生成的 `log-level: ''` 坑过 ——
那种字符串拼接式的配置生成迟早出这类错。

原子性设计：
- 写入 `config.yaml.new`
- `mihomo -t -f config.yaml.new` 校验
- 通过 → 改名覆盖 `config.yaml` → reload
- 失败 → 保留旧配置，UI 显示 mihomo 的原始报错

### 3.5 订阅处理

机场订阅返回三种格式，需全部支持：

| 格式 | 判据 | 处理 |
|------|------|------|
| 完整 YAML | 含 `proxies:` 或 `proxy-providers:` | 直接取节点 |
| base64 | 解码后是上面两者之一 | 解码再判|
| SIP008（ss 订阅） | JSON with `servers[]` | 转成 ss 节点 |

**合并策略**（用户定，规则由本项目管理，订阅只提供节点）：

```
最终 proxies       = 内置节点 + 各订阅的节点
最终 proxy-groups  = 本项目配置的组（订阅节点自动加入候选池）
最终 rules         = 本项目的规则（订阅的 rules 一律忽略）
```

理由：机场订阅的 `rules` 通常质量不高且会随更新变动；
用户配置应独立保存，**下次更新订阅不覆盖**。

沿用 OpenClash 订阅元数据的字段设计（§2.3 第 3 点）。

### 3.6 目录与打包

```
/opt/mihomo-client/
├── bin/mihomo-client        # 单二进制（Rust 静态链接）
├── bin/mihomo               # 内核二进制
├── etc/
│   ├── config.yaml          # 用户配置（本项目 schema）
│   └── subscriptions.yaml   # 订阅列表与元数据
├── var/
│   ├── config.gen.yaml      # 渲染产物（给 mihomo 用）
│   └── mihomo/              # mihomo 工作目录（geodata、ruleset）
└── web/                     # Web UI 静态文件
/etc/systemd/system/mihomo-client.service
```

打包 deb（后续可加 rpm）。

## 4. 待验证的风险（动手前必须先做）

按优先级：

1. **旁路由真实验证** —— 172.20.0.101 做旁路由，.2 或 Windows 做客户端，
   验证：转发链路、环路、UDP/QUIC、DNS 劫持。
   **这是本项目最容易失败的地方。**
2. **`tun.stack` 选哪个** —— `system` 性能最好但依赖系统协议栈；
   `mixed`（tcp=system, udp=gvisor）体验折中；`gvisor` 最安全但最慢。
   需要实测。
3. **订阅合并的命名冲突** —— 多订阅节点同名怎么办
   （方案：加来源前缀，如 `HK-01@机场A`）。
4. **`/etc/resolv.conf` 与 `dns.listen` 的关系** —— 旁路由下
   要不要接管本机 DNS、怎么避免 systemd-resolved 冲突。
5. **Web UI 与内核 API 的鉴权分层** —— 浏览器不能直连内核 API
   （会暴露 secret），必须由客户端 API 代理。

## 5. 建议的实施顺序

1. **打通最小闭环**：Rust CLI + YAML 渲染 + `mihomo -t` 校验 + systemd 拉起
   （本机代理模式，用 127.0.0.1 mixed-port）。
2. **加订阅**：抓取 + 格式识别 + 节点合并。
3. **加 RESTful API 代理 + Web UI**：先只做「运行控制 + 节点选择 + 订阅管理」。
4. **加规则配置**：规则编辑 + rule-provider 管理。
5. **旁路由**：`tun` 接入 + 环路处理 + 用 .101/.2 实机验证。
6. **诊断与可观测**：连接/日志/出口IP/自检。

前 4 步不碰旁路由，风险可控，能独立交付可用版本。
